# Product behavior

Status: Active

Product scope: the v1 behavior confirmed by the owner. The complete P1-M5 implementation contract is linked below.

## Confirmed v1 behavior

- Diary Snippet detail has a full-width Delete Diary Snippet button below Metadata. Tapping it reveals an inline warning with Delete Diary Snippet and Cancel, without an overlay. Explicit confirmation permanently removes that verified diary text/audio pair from iCloud, including an eligible legacy pair, while preserving unrelated files. Pending save/edit work must settle first. Stop replay before deletion, prevent duplicate requests, and return to the refreshed Main collection on success. Failures show a reason; changed or unsafe pairs are preserved. Leaving the screen or active scene disarms unconfirmed deletion. See [M20 Task 21](phase-1/milestone-20-enhancements-fixes-refactoring-architecture.md#task-21-delete-a-diary-snippet-from-detail).

- Settings → Danger Zone has two independent, explicit inline confirmations. Purge Active Folder Contents removes every descendant, including non-app files, while keeping the selected folder/bookmark. Purge Internal Staging removes app-owned pending/failed audio, unsaved drafts, receipts and staging records while keeping saved iCloud assets, Settings and installed models. Neither operation starts while capture, transcription, title adoption or saving owns work. Folder purge also requires staging to finish or be explicitly purged separately, preventing automatic republication. Validated completed queue history remains intact and does not block folder purge. Cancel, navigation and scene departure disarm unconfirmed actions. Partial or interrupted purges pause recording and processing across relaunch until the same purge is explicitly retried; unavailable recovery data fails closed. See the [M20 purge contract](phase-1/milestone-20-enhancements-fixes-refactoring-architecture.md#task-9-danger-zone-purge-actions-in-settings).

### Target and recording

- V1 targets iPhone 17 Pro Max running iOS 27.0.1 or later, without iPad support.
- On first launch, explain why recording needs the microphone and request microphone permission. If permission is denied, let the user continue using non-recording parts of the app; the Record control explains how to enable the microphone in system Settings. Recording begins only after permission is granted.
- A user can record up to five minutes of audio without a network connection. Target mono AAC in `.m4a` at 44.1 kHz and approximately 64 kb/s. P1-M6 established short-file viability for the selected Cohere direction but did not establish five-minute quality; P1-M12 must process long input in bounded chunks and verify complete seam handling.
- Locking the iPhone or switching away from the app does not stop an active recording. Capture continues until Stop & Transcribe, the five-minute limit, or an audio interruption. If capture ends while locked, finalize the audio and durably queue it immediately without waiting for unlock; P1-M9 must validate the active-file and journal protection on a physical device.
- At five minutes, stop recording and queue the finalized audio automatically. If an audio interruption ends recording early, automatically queue a playable partial recording. If the partial file cannot be played, retain it in Failed Recordings and show the reason beside its entry.
- The app may keep the recording temporarily in private local storage while offline or while its iCloud destination is unavailable.
- Exclude pending audio and unsaved diary drafts from device backup, accepting that phone loss can permanently lose pending work. Exclusion does not erase copies already present in older backups. Identify another-install restored work with a random Keychain installation ID marked `ThisDeviceOnly`. Quarantine restored jobs in Pending Recordings with a review-required state and Resume/Remove actions before any automatic transcription or iCloud save; Resume creates a fresh attempt using current Settings.
- A user provides an en-US or ko-KR recording language hint where possible. Store the user's hint with the recording, pass a corresponding value to a transcription method when supported, and save only this hint as the asset language value.

### Transcription

- V1 offers a dedicated Transcription Settings screen with exactly None, Apple Local, Cohere Q4, and Cohere Q5 choices. Selection is persisted separately from installation/readiness, and None or an unready choice leaves recordings pending without automatic fallback. Apple on-device transcription and the on-device Cohere Transcribe method remain local. Cohere Q4 and Q5 use the same approved `transcribe.cpp`/Metal runtime with separate pinned model descriptors and installations. Require an explicit `en` or `ko` hint, do not fall back to CPU automatically, treat truncated output as failure, and use silence-aware chunks no longer than 45 seconds until longer input is proven complete on the target phone. Provide readiness and model-download controls in the child screen, showing each selected model's pinned download size and preflighting available storage before installation. Apple system assets show installation progress; Apple does not expose a documented pre-download size or required-space estimate. The Cohere method runs locally after its model is installed and does not upload recordings for transcription. P1-M12 still must validate production provenance, cancellation, chunk seams, and long-input completeness.
- The Settings screen lets a user preflight Apple on-device transcription, download a needed language model, wait for readiness, and see the reason when it is unavailable. If Apple transcription is unavailable for a queued recording, ask the user to choose among available approved methods; never switch automatically. Approved Cohere model versions and cryptographic digests are pinned in the app; adding a version requires an app update.
- A queued recording uses the transcription method and method settings selected when processing starts. Refresh readiness when Settings opens, when the app becomes active, and immediately before claiming a job. Record the method, model or conversion, and settings actually used with the result. If a local model is missing or not ready, keep the job pending and offer model installation or selection of another ready approved method; never switch methods automatically.
- Transcription runs automatically, oldest ready recording first, only while the app is open. A waiting or failed recording does not block a newer ready one. Missing method/model/destination/upload proof waits; decoder/runtime failure, unusable text, and the ten-minute cutoff fail with audio retained. A queue-store failure pauses the queue. Each processing attempt settles its own job before the queue advances; a failed job does not retry automatically or hold the worker. Apply a ten-minute hard cutoff to a nonsettling local inference attempt and advance only after the adapter relinquishes work. Recordings and queue state survive offline periods and app closure. Request notification permission only when the first reminder is needed. Schedule generic text “You have pending diary work.” for the next local day at the same local wall-clock time the user left the app, recomputing on reopen for the current timezone and next valid DST time. Cancel it if all pending work finishes before it fires. If permission is denied, keep pending work visible and offer a nonblocking system Settings path without repeatedly asking.
- A v1 transcription failure keeps the audio in a failed queue state and offers manual retry; local model unavailability keeps the job pending with a reason. Create no diary Markdown until transcription produces usable text.
- A manual transcription retry uses the method and settings current when the user starts that retry. Manual retries have no fixed count limit while the recording remains.
- If transcription yields no usable words, retain the audio as a failed recording, create no asset, and offer manual retry. Show the reason beside the entry in Failed Recordings.
- Allow the user to remove a pending or failed recording and its private audio after confirmation inline in that recording's screen. Tapping Remove reveals the question and explicit Remove Recording and Cancel actions inside the entry, without an overlay dialog; only the confirmation action requests removal. Removal must stop or invalidate any processing of that recording so it cannot later create an asset. For an in-flight recording, show Cancelling until work stops and removal completes.
- If removal is confirmed while a save is in progress, cancel an unverified save. If the complete asset was already verified before confirmation, preserve it and explain that the recording has completed rather than removing that saved asset.
- Transcription output initializes the diary's single managed text body. Prefer an Apple on-device AI summary of the whole body for its read-only title when the model is available; if the model is unavailable or returns an empty or failed result, shorten the body's first sentence locally with an ellipsis. Both title paths have a strict 30-displayed-character maximum measured in Swift extended grapheme clusters, counting any ellipsis within the limit. Save the Markdown and audio asset automatically without a pre-save review step, including after an AI title failure. User edits replace the body; regenerate the title using the same policy on save. An emptied body may be saved with the title "Untitled". Do not keep a separate original transcript after the managed text is written.
- Generate an AI title in the current diary body's language, even if that differs from the recording's language hint. Use prompt revision `title-v1` to request one faithful concise phrase with no quotation marks, prefix, invented facts, emoji, or ending punctuation. For a long body, use at most eight token-aware 2,000-token chunks and two summary passes, with 80-grapheme intermediate summaries, 128 intermediate output tokens, 64 final output tokens, and a 30-second total budget. Every body part must contribute within that bound. Require language confidence of at least 0.8; unsupported, uncertain, wrong-language, empty, or failed output uses the fallback. The fallback trims the body, uses the native sentence tokenizer, then the first nonempty text if necessary. Truncate an overlong title to 29 grapheme clusters plus `…` rather than asking the model again. Once saved, a fallback title stays until the next body save.

### Assets and metadata

- Diary Snippet is the only confirmed v1 asset type. The architecture allows other asset types later, but their behavior is not defined here.
- Show an existing legacy Markdown file with exactly one safe plausible audio sibling as a read-only Diary Snippet and leave its files untouched. Give it only an ephemeral path-based catalog identity. Put legacy Markdown with zero or multiple plausible audio siblings in Incomplete Diary Snippets, read-only and preserved, with the ambiguity explained.
- V1 stores assets in a user-selected iCloud folder. The user may select any positively verified iCloud Drive folder or create one; reject local, third-party, and ambiguous providers. Before the first folder-backed save, show a one-time notice that diary text, audio, and optional exact location are readable files and anyone with folder access may read them.
- Before the first recording, require the user to select or create an iCloud destination folder. Treat ordinary network or provider errors as temporary. Offer explicit replacement for a pending recording only after the user confirms that its original folder was removed or access was revoked; the app must not infer permanent loss from repeated transient failures.
- Changing the selected folder leaves existing assets in the old folder. The app lists only assets in the active folder.
- Main shows the full active-folder diary collection with on-demand loading and infinite scroll. A one-line notice bar at its top reports queued recordings, in-app transcription, and recovery attention, rotating one message every 10 seconds when several apply. Rotation pauses for VoiceOver or Reduce Motion; queued and processing messages open Pending Recordings, and a recovery message opens its relevant recovery screen. All shows no diary snippets for now. Settings opens only from All, and a floating Record control is on Main.
- Pending Recordings, Failed Recordings, Incomplete Diary Snippets, and Conflicting Versions are separate screens opened from All. Incomplete Diary Snippets also contains safe unsupported assets, malformed required v1 assets without repair copies, and ambiguous legacy audio, all read-only and preserved. Main shows only notice-bar attention for recovery. Diary Snippet detail shows Title and Diary body first, Favorite beside Title, and Audio replay inside bottom Metadata. Metadata also shows read-only recording start date/time, duration, language hint, and available place and weather, omitting unavailable optional values.
- During capture, Stop & Transcribe is the only user control; it stops and queues playable audio for automatic processing while the app is open. Pause/resume and discard controls are outside v1. The exact v1 empty-state messages are “Benefits are coming later.”, “Calendar is coming later.”, and “Plugins are coming later.” No Main Toolbar is specified.
- A recording keeps the iCloud destination folder selected when recording began, even if the active folder changes before processing finishes. If that destination is unavailable, keep the result pending and ask the user to restore access. When a result is saved into a former active folder, show a nonblocking in-app completion banner naming that folder.
- If a recording's destination is temporarily unavailable, continue local transcription and prepare the managed diary text, then keep the private draft pending until it can be saved.
- The Markdown body is the only managed diary text. Its automatically generated title is read-only. The editor changes only the body; Favorite has a separate on/off toggle. Record, Stop & Transcribe, Settings, Pending Recordings, Failed Recordings, Incomplete Diary Snippets, Conflicting Versions, and Favorite are exact v1 labels.
- Preserve the existing UTC `year/month/day` layout. Generate a random UUID v4 serialized as lowercase canonical hyphenated text. Name the Markdown `YYYY-MM-DD_HH-mm-ss-<uuid>.md`, its sibling directory `YYYY-MM-DD_HH-mm-ss-<uuid>.assets`, and its audio `<uuid>.m4a`. Write all instants as RFC 3339 UTC at whole-second precision with `Z`.
- Store schema version, title and origin, Favorite, recording details, explicit audio reference, and effective transcription provenance in flat YAML front matter. The [P1-M5 schema contract](phase-1/milestone-05-decisions-architecture.md#diary-snippet-schema-contract) owns the exact keys, identifiers, serialization, and validation rules.
- In a new Diary Snippet, `language` and `transcription_language_hint` both store the recording's explicit `en-US` or `ko-KR` hint and remain recording metadata after body edits. The title still uses the body's current language, even when it differs from that hint.
- Preserve unknown flat scalar keys without interpreting them. Unsafe or malformed front matter is rejected under the schema contract; unsupported schema/kind/method/title-origin values remain untouched and appear read-only in Incomplete Diary Snippets with a reason. Never rewrite legacy names, including their millisecond timestamp forms.
- Set `created_at` to the instant recording started and group assets by that instant's date in the user's local calendar. Set `updated_at` when a saved text or metadata edit occurs; an iCloud sync or download alone does not change it. File and directory names remain UTC.
- Location and weather are optional, permission-based metadata describing recording start. Begin acquisition then and accept results only before initial asset commit. Request location permission during first launch and provide a Settings control; denial does not block recording. Accept a location sample no older than five minutes with horizontal accuracy no worse than 500 m. Save exact coordinates and display them if place lookup fails. Accept weather only within 60 minutes of recording start, store Celsius, display using the system measurement locale, and show Apple Weather attribution below it in Metadata. Omit unavailable complete optional groups and do not backfill late context.
- Recorded-audio replay offers play/pause, seeking, and elapsed and total time.
- If one complete conflicting pair is unambiguously later by both iCloud modification times, select it automatically and remove the obsolete version only after the chosen pair is verified and both files report successful upload. Device clock differences can make timestamp order differ from actual edit order. If conflict times are equal, missing, or cross-ordered, keep both and show one version per vertically scrollable tab in Conflicting Versions. The user chooses one; confirm before removing the other. If an iCloud write leaves an incomplete Diary Snippet bundle, repair it from the retained local candidate when the app reopens. If no retained local candidate exists, keep the incomplete files and flag the item in Incomplete Diary Snippets; show whichever diary text or playable audio survives read-only, explain what is missing, and offer removal only after confirmation.
- If saving a completed diary draft fails because iCloud access is unavailable, retain its private Markdown and audio files and retry saving them automatically when access returns, without repeating transcription. Delete the private staging folder only after the complete iCloud pair is verified locally and both Markdown and audio report successful upload; then delete it immediately. If upload cannot be verified, retain staging for recovery. While the app is active, retry transient access/upload/protected-data waits automatically with increasing delays; returning to the app also resumes verification. Keep Retry Verification for an immediate manual check. Failed transcription and ambiguous/conflicting files still require their existing recovery actions. The device prototype must confirm whether the upload signal works in a user-picked iCloud Drive folder.
- Render diary Markdown as inert native content: no interactive links, HTML or script execution, remote images, or automatic fetches.
- Resource limits are 64 KiB front matter, 1 MiB body, 64 MiB audio, 64 keys, 8 KiB per scalar, 301 seconds for new-schema audio, 50 catalog candidates per page, and a 100 MiB free-space reserve before recording. There is no collection or pending-job count cap. Stream legacy audio only up to 60 minutes and 64 MiB; otherwise show its text with audio unavailable.
- When the recording reserve is unavailable, show “Not enough storage to start recording.” with Review Pending Recordings and OK.

### Future work: hosted Qwen transcription

Hosted Qwen transcription is outside v1. Earlier owner decisions remain recorded for a future release: the user supplies a key stored in Keychain until removed, chooses Beijing or Singapore and supported model controls, and consents before audio upload. Consent revocation deletes the key; key removal fails pending Qwen jobs while retaining audio. A user-set budget blocks requests that would exceed this app's estimated monthly usage and resets at the start of the user's local calendar month. Only temporary network or server transcription failures receive up to three automatic retries. These controls and cloud jobs are not shown or created in v1.
