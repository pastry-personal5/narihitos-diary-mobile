# P1-M14: iCloud commit and reconciliation approach

Status: In progress

This plan adds a coordinated external-pair store and a resumable save coordinator behind the existing destination and queue boundaries. Durable local evidence, not an in-memory callback or filename, controls completion and cleanup.

## Boundaries and commit record

The application coordinator consumes a verified M13 draft handle, a leased audio handle, the current queue claim, and opaque destination access. Its ports expose typed pair-write, pair-read, upload-observation, snapshot, and cleanup outcomes; domain/application code receives no URL, bookmark, `NSFileCoordinator`, or provider error. The platform adapter alone resolves the original capture snapshot, balances security scopes, coordinates access, validates file identities and containment at use time, and maps provider failures to sanitized states. This snapshot loan has its own destination revision; a later Settings selection cannot revoke or redirect it, while an iCloud account/identity change or explicit per-job replacement invalidates it. Reuse M8's positive folder predicate for each loan, including stale-bookmark renewal, without using the active-selection generation as the job's destination authority. The M7 codec validates Markdown and references; the M9 audio verifier supplies actual playable-source identity.

Extend the versioned per-job record with an app-owned commit intent: stable asset ID and UTC pair names derived from the verified draft, source Markdown/audio lengths and cryptographic digests, attempt/generation, installation binding, destination/body revisions, original destination snapshot reference, and the exact external identities/versions observed during creation or repair. Store only bounded identity evidence, never an arbitrary deletion path or a front-matter hash as authority. Migration leaves old jobs readable and cannot invent commit success. Keep the retained M13 draft binding and audio available throughout verification.

## Publication and upload proof

1. Reconcile tombstones, restore quarantine, and the verified draft/audio claim. Recheck the claim after every asynchronous operation; destination availability is a save prerequisite, not a prerequisite for local transcription or draft creation. Snapshot the original destination and current revisions. A changed active folder has no effect.
2. Acquire the M10 per-job mutation barrier before the first destination mutation and retain ownership through pair verification, upload proof, and durable completion during an active save attempt. Resolve the recorded destination with M8's positive iCloud/account checks. Bound provider waits and upload observation. If proof is unavailable, persist a waiting state while retaining staging, close observers, and release the barrier only after every coordinated operation relinquishes; retry later under a fresh barrier claim and generation, beginning with coordinated pair verification. A timed-out operation that has not relinquished keeps ownership uncertain and cannot be acknowledged as cancelled or started again concurrently. A removal or retarget accepted first invalidates this save attempt.
3. Persist the commit intent before writing. Coordinate each resource. Validate parent and final target without following an unsafe reference. Create the expected audio exclusively, then the Markdown, or replace only an exact version already owned by this commit. Write into provider-coordinated temporary targets where supported and publish with checked identity; never use unchecked overwrite or infer ownership from a matching asset ID. If either write fails, retain private staging and the observed partial state.
4. Reopen both files through coordinated reads, decode the Markdown, check its explicit audio filename and canonical layout, verify the actual audio and both expected lengths/digests, and record the observed file identities/versions. A file changed after the write is a conflict or recovery item. A complete pair that matches an earlier intent is reused rather than written again.
5. Observe upload success independently for the two exact versions just verified. Bind each observation to its file identity/version and invalidate earlier success if that resource changes; never combine reports from different pair revisions. Recheck identities and bytes after interruption or provider change and immediately before completion. Missing or ambiguous status means `Waiting for iCloud upload verification.` and `Retry Verification`; a destination outage uses `Waiting for access to {folder}.` and `Restore Access`. These states do not block other ready jobs. The physical iPhone prototype must establish the platform signal and its version-binding behavior for a user-picked folder; no local-file, sync-indicator, elapsed-time, or network-availability substitute counts as proof. If the signal reports only a file-level status without a trustworthy version, combine it with a coordinated identity/content check immediately before durable completion and demonstrate on device that a replacement between reports cannot pass; otherwise keep the gate open for owner review.
6. Recheck claim and versions, durably record verified completion, then remove only the job-owned private staging and release its destination snapshot. Record cleanup progress separately from save completion: an interrupted cleanup resumes from recorded completion without reopening a write path or republishing. If the queue store cannot persist proof, retain staging and reverify later. If cleanup cannot finish, retain a cleanup-pending state and retry; do not describe private deletion as complete. Emit the former-folder banner event only once after durable completion.

## Reopen, repair, and conflicts

Reconciliation inspects each job independently before scheduling. A matching complete pair resumes at local/upload verification. An owned audio-only or Markdown-only pair can be repaired from the retained candidate only if the commit intent, current job revisions, external file identities/versions, and expected bytes all agree. Independently discovered external incomplete pairs, including those seen on a second device with no private candidate, receive a bounded read-only classification from the same pair validator; a missing candidate never authorizes reconstruction. M15's catalog enumerates them and M17 presents the typed result and confirmed removal. External edits, unsafe references, unknown schemas, duplicate IDs in different resources, provider version uncertainty, or mismatched ownership stop automatic repair and cleanup. A queue-store failure pauses durable advancement; it never turns an observed file into a completed job.

The read-only inspector can use either the current active folder or a pending job's retained capture-time destination snapshot. The latter reports a typed partial pair even after Settings changes folders; inspection alone never grants ownership or repair authority. New commit intents carry distinct random per-file creation markers. The writer best-effort stores a marker bound to its device and inode as a file extended attribute before syncing the newly created file. If the queue version checkpoint is interrupted, a retry may adopt that exact file only after checking the marker, byte count, digest, unresolved-conflict state, and stable coordinated file identity. A copied marker on another inode cannot claim the file. A missing or unsupported marker keeps the existing collision behavior and typed read-only recovery path; an older commit intent without markers remains readable but cannot claim an uncheckpointed file. Target-iPhone evidence must establish whether the user-picked provider preserves these markers before claiming automatic checkpoint recovery there.

Snapshot each complete conflict candidate as a protected, backup-excluded Markdown/audio pair with its own verified binding and observed iCloud modification times for both resources. Validate each pair and its referenced audio before applying the approved time rule. Select a later whole pair only when its iCloud time ordering is unambiguous; equal, missing, or cross-ordered resource times stay separate for M17's user choice. Do not combine Markdown from one candidate with audio from another. Publish and verify the chosen pair, including both upload reports, before deleting an obsolete external version or private snapshot. For an unambiguous later pair, remove the obsolete version automatically after this proof; for a user-chosen ambiguous pair, M17 confirms removal first. Revalidate exact resource identity/version immediately before deletion; changed or shared resources stay in recovery. M14 emits typed recovery records that identify surviving read-only content and missing components; M17 owns presentation and ambiguous-choice confirmation. M16's editor passes its read version to this same expected-version/conflict port.

The conflict inspector enumerates the current and unresolved `NSFileVersion` entries for each resource under the capture-time destination loan. It reads each version with bounded coordination, requires an explicit audio digest in each Markdown version, pairs only a unique digest match, and captures two complete pairs into idempotent private snapshots. Two distinct Markdown versions may share the same uniquely matched audio version, as in a text-only edit; both become separate complete snapshots. The existing equal-audio-time policy still requires explicit choice. Multiple audio versions with the same digest remain ambiguous and block pairing. The save coordinator invokes this inspector when a provider conflict blocks publication and durably binds the snapshot IDs, observed current file versions, provider-version keys, attempt, and revisions to the job. Unambiguous time ordering records the selected snapshot and authorizes automatic obsolete removal after proof; equal, missing, or cross-ordered times leave selection and removal confirmation open. An explicit choice validates both snapshots and rechecks current external versions before persisting the selected ID; M17 confirms removal for that case. The conflict pair store checks the expected current version inside coordinated audio-then-Markdown replacement, marks each new inode for interrupted-checkpoint recovery, and reopens the selected pair. It waits for two exact-version upload reports and a final unchanged check before recording proof. The version cleaner then removes only recognized, content-checked obsolete `NSFileVersion` entries, blocking unknown conflicts; only after this cleanup is durable does the job advance to saved and remove its protected pair snapshots and capture staging. Target-iPhone provider behavior and adversarial cleanup evidence remain open.

## Verification sequence

The commit and independent recovery adapters use asynchronous `NSFileCoordinator` intents on a background operation queue. A deadline cancels the coordinator and waits for the callback and accessor to settle before releasing the per-job barrier; a provider that never settles keeps the barrier and `Cancelling` state. `NSFileVersion` exposes per-file conflicts, so a whole Markdown/audio candidate must be positively paired and validated before the modification-time rule or obsolete-version removal can run; independent versions may not be combined by guesswork.

1. Add typed commit intent and store ports, queue migration, and a fake coordinated provider. Test one successful save, active-folder changes during a snapshot loan, account changes, waiting jobs, and duplicate IDs without adding a dependency.
2. Implement the platform coordinator behind M8's destination access. Inject failures at intent persistence, each file write, reopen, both upload reports, completion persistence, and staging cleanup; relaunch after each point.
3. Add version-checked repair, typed recovery records for both job-owned and independently discovered pairs, and protected pair snapshots. Test equal/missing/comparable/cross-ordered times, shared audio, unsafe references, external mutation between upload observation and completion or deletion, removal/retarget races, and bounded coordination that never falsely acknowledges settlement. Exercise waiting-state barrier release and a fresh fenced verification attempt without duplicate writes.
4. Run affected tests while iterating, then the full lint and simulator gate once. On a target iPhone, execute [M14-D01–M14-D07](milestone-14-icloud-commit-reconciliation-device-evidence.md), recording only redacted state, version class, timing, and evidence method. A missing per-file upload signal or failure of the M8 folder identity predicate requires owner review before changing the approved outcome.

## Implementation review refinements (2026-11-02)

Interrupted conflict publication checkpoints the second stable, verified observation directly; it does not perform a third unchecked read that could adopt changed provider content. File observation constructs a fresh file URL independently of caller-cached resource values, then clears resource-value caches before and after hashing so the stability comparison uses freshly requested metadata. An unavailable original file remains a retryable provider wait, while symlinks and nonregular resources remain unsafe. These checks supplement, and do not replace, the open target-iPhone upload-signal evidence.

Confirmed pending-recording removal also removes the two positively identified private conflict snapshots before deleting its capture workspace and queue record. Asset/version checks fence deletion, partial cleanup is idempotent, and missing snapshot-store access retains the removal job for retry. This path never removes external provider versions.
