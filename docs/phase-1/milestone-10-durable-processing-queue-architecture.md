# P1-M10: Durable processing queue approach

Status: Active

Build the queue as an application coordinator over confined persistence, a compile-time method registry, and cancellable attempt adapters. This plan separates the durable receipt-to-job handoff from method-specific inference and later diary/iCloud publication.

## Boundaries and record

| Area | Owns | Excludes |
|---|---|---|
| Domain/Application | Job identity, ordering, transition policy, attempt generation, readiness decision, retry, removal barrier, sanitized projection | SwiftUI, Keychain APIs, URLs, audio decoding, provider bookmarks |
| Queue repository adapter | Bounded versioned records, atomic replacement, recovery inventory, backup/protection verification, per-job mutation serialization | Method choice or user-facing reason text |
| Installation identity adapter | Random `ThisDeviceOnly` Keychain value and typed match/mismatch/unavailable result | Raw identity in UI or diagnostics |
| Method registry/adapters | Registered descriptors, readiness, accepted audio/language, cancellable inference, effective provenance | Queue order, retargeting, asset publication |
| Presentation | Pending/Failed counts and entries, review-required state, Cancelling and paused-work messages | Durable truth or raw platform errors |

The queue record uses the existing M9 workspace ID as job ID and references its capture receipt and fixed audio artifact. It contains a schema version; installation binding; immutable recording start, language, destination reference, and measured audio metadata; durable state and reason code; attempt ID/generation; selected method ID; namespaced versioned effective settings and model/conversion identity; and later-stage draft/commit references when those milestones supply them. A retry count may aid diagnostics but must never gate manual retry. Bound every field and decode before access. The repository owns path derivation from validated IDs; persisted records cannot nominate arbitrary paths or files for deletion. Keep state changes and required artifact checks in one recoverable transaction or journal, verify the replacement and its attributes before projecting success, and preserve recovery copies on uncertain failure. There is no policy cap on pending-job count; scan and decode incrementally with per-record bounds so one corrupt record or a large inventory does not block other work.

Adoption scans M9 settled receipts after M9 reconciliation, checks that each receipt and audio are still valid and belong to the same workspace, then creates a queue record with create-if-absent semantics. An existing matching record wins; a conflicting record is quarantined. M9 failed receipts and unresolved audio orphans stay in recovery inventory; a failed receipt is never made ready just because its audio exists. Until adoption is durable, M9's receipt remains the source of truth; afterward, a single queue projection owns Pending/Failed display so a relaunch cannot show duplicate entries. Do not convert protected-data inaccessibility into a missing-file conclusion. Keep the independent destination snapshot retained until later verified commit or confirmed cleanup; a change to Settings' active folder never rewrites it.

## Installation and restore

Create the installation ID before new capture starts and store it as a random Keychain item with `ThisDeviceOnly`. Extend the M9 capture-start marker and receipt with the binding before accepting audio, without moving the audio or changing its immutable identity; locked settlement copies the already durable binding and does not query Keychain. Perform this as a compatible journal-schema migration: old unbound markers and receipts remain readable and reviewable, and no existing receipt is silently stamped with the new identity. A Keychain read that is temporarily unavailable pauses adoption and claims without deciding that the ID is absent; a failed ID creation or write blocks new capture. Preserve all existing files in either case. Once the Keychain is available, compare each record's or unadopted receipt's binding with the current ID before invoking a method or resolving its destination. A mismatch or genuinely missing binding means review-required quarantine, including unbound M9-era receipts and records from older backups; unknown or corrupt records are separately isolated. Resume is an explicit intent that validates the retained receipt/audio and its ownership, binds the current installation, increments the attempt generation, and snapshots current Settings at its next claim. If backup exclusion left no playable audio, retain a reviewable reason and refuse Resume. A resumed job must never reuse a former installation's effective method/settings. M17 will provide the complete Resume/Remove presentation; M10 supplies the safe intents and a minimal reachable review state.

## Scheduling and attempt ownership

1. On app activation, reconcile capture and queue artifacts, refresh registered method readiness, and build the ready set. Refresh readiness on Settings entry too, and reconsider waiting jobs when a model install, method selection, unlock, or other relevant prerequisite changes. Sort by persisted start/order then stable ID. Do not start work while the app is inactive or while durable storage is paused. Reconsideration must not turn a failed attempt into an automatic retry.
2. Before claiming a job, resolve current Settings, refresh the selected method's readiness, and check language/audio compatibility. Unknown or unready methods transition to waiting with a typed reason and do not consume the worker. Never choose another method on the user's behalf. Persist the selected method and effective snapshot with a new attempt generation before calling the adapter. If persistence fails, the adapter is not called. A crash after the claim is durable but before adapter start is reconciled as an interrupted attempt, without assuming inference ran or creating an automatic failure loop.
3. Give one active attempt a cancellation token and a ten-minute deadline. A success result is accepted only if job ID, generation, method, destination revision, and body revision still match. M10 can deliver a method-neutral result to a fake downstream sink; P1-M13 will persist the managed draft before advancing the production job.
4. A local inference failure or unusable text leaves audio and a sanitized entry-level reason in Failed. A missing prerequisite stays Pending and waiting. Timeout invalidates the generation, requests cancellation, and waits for the adapter's explicit relinquishment before releasing worker ownership. If it cannot relinquish, retain a timeout/recovery state and do not start another inference concurrently or pretend the cutoff ended the work. Reserve the visible `Cancelling` state for confirmed user removal.
5. On settlement, durably update the one job, release ownership, and select the next ready job. A failed transition write pauses the whole queue; it cannot report settled progress from in-memory state. No automatic retry loop exists. Manual retry requires an explicit intent and rechecks current Settings.

Capture settlement while locked remains M9's path. M10 does not require Keychain or protected queue access to finish that receipt; adoption waits for protected data and app activation when needed. Leaving the app active state stops new claims, not M9 capture. A process ending mid-attempt leaves a durable attempt record; relaunch invalidates the old generation and reconciles audio/draft truth before requeue or failure. It does not trust an in-memory callback from before relaunch.

## Removal and later stages

The per-job barrier covers first destination mutation through local pair verification, upload proof, and completion. M10 defines barrier ownership, attempt invalidation, destination/body revisions, and a durable removal tombstone. M14 must use the barrier for every destination write and repair; M17 must use it for per-job destination replacement. A confirmed removal accepted first prevents publication and cancels unverified work. A fully verified completion first makes the recording no longer removable as pending work and reports that it was saved. A removal request during mutation waits for the barrier and shows Cancelling. The tombstone remains until the adapter has relinquished every file and only positively identified private artifacts have been cleaned. A bounded wait may return a recoverable pending state, never an assertion that cancellation or deletion completed.

M10's repository reserves versioned extension points for future `readyToSave`, `waitingForDestination`, `saving`, `saveFailed`, and `completed` transitions; it does not need to fabricate production states before M13/M14 supply durable drafts and verified publication. A destination outage must not block local transcription; save selection is independent of transcription selection once those stages exist. M14 owns actual iCloud mutation, incomplete-pair repair, upload evidence, and final staging deletion. M17 owns complete recovery screens and confirmed per-job retargeting. M18 owns notification scheduling and generic reminder text.

## Verification sequence

1. Add the record, repository, installation-ID port, and adoption/reconciliation tests. Inject crashes and storage faults at every replacement boundary.
2. Add the method registry, settings snapshot, readiness policy, and scheduler with fake adapters. Test ordering, foreground gating, three-job isolation, timeout, cancellation acknowledgement, late callbacks, and retry.
3. Add barrier/tombstone removal intents and minimal truthful Pending/Failed projection. Test removal against fake publication and stalled operations; inspect UI accessibility and diagnostics.
4. Run focused tests while iterating, then delegate the exact repository gate to `test_runner`. Record a redacted physical backup/restore outcome and, if pending work is absent as intended, use a controlled prior-install fixture on the device to exercise quarantine. Label the two observations separately; do not substitute simulator behavior for either device check.

The trial records device/OS/app revision, whether an actual backup restored any pending work, and, for a controlled prior-install fixture, whether the installation binding mismatched, whether the job remained quarantined before Resume, and whether Resume or Remove acted only after an explicit user action. A fixture must contain synthetic playable audio and a valid receipt so it tests the gate rather than merely failing audio validation. Never record Keychain bytes, audio, transcript, folder names, bookmarks, paths, or raw logs. Production Apple and Cohere attempts, real cancellation settlement, and complete diary/iCloud behavior remain evidence gates in P1-M11–P1-M14 and P1-M19.
