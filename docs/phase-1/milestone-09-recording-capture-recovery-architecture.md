# P1-M9: Recording and capture recovery approach

Status: Active

Separate capture policy from AVFoundation and private-file mechanics, then settle each recording through one durable handoff. Device trials select a lock-compatible protection mechanism; the plan does not assume that a simulator or a requested encoder setting proves the approved behavior.

## Boundaries and durable handoff

| Area | Owns | Excludes |
|---|---|---|
| Domain/Application | Start prerequisites, capture identity, immutable recording-start metadata, stop arbitration, validated capture outcome, receipt/reconciliation policy | AVFoundation, URLs, SwiftUI, provider bookmarks, file-protection constants |
| Apple audio adapter | Audio session, interruption route, encoder, elapsed/level samples, actual file inspection and playability probe | Queue scheduling, transcription, iCloud save |
| Private capture adapter | Confined streaming file and capture receipt, attributes, backup exclusion, atomic settlement, orphan inventory | Arbitrary paths from persisted state, deletion of uncertain audio |
| Presentation | Language-specific Record controls and gate, capture status, Stop & Transcribe, sanitized recovery routing | Raw audio bytes, bookmarks, provider URLs |

M7's `PrivateWorkspacePort` is Data-oriented and caps an artifact at 64 MiB. Extend it through an inward streaming-capture capability rather than buffering the whole recording in memory or passing a file URL to the application use case. The adapter may privately issue a scoped file target to AVFoundation and must revalidate the workspace and resulting file before settlement. Use a fixed adapter-owned audio filename and an opaque handle at the core boundary. M8 currently persists only the active destination record: replacing the active folder can overwrite its bookmark. M9 must add an opaque, independently persisted capture-time destination snapshot to the inward port and retain the original bookmark and account-identity evidence behind the adapter. Creating that snapshot and recording its reference in the capture marker must settle before audio starts. A failed snapshot blocks capture. Folder changes cannot rewrite or discard a snapshot held by pending capture work; M14/M17 own eventual publication, explicit per-job replacement, and safe release. The receipt retains the snapshot reference, not merely the display name, `DestinationID`, or currently active folder. Revalidate it when used; a stored snapshot is not permanent proof of access.

Separate destination-record validity from immediate provider reachability. A previously accepted iCloud folder with intact local identity evidence can be snapshotted while an ordinary network/provider outage prevents a live probe; the resulting recording waits for access when publication later needs the folder. Do not turn a missing record, corrupt bookmark, known account mismatch, or known revoked scope into an offline exception. A temporary error alone cannot establish permanent loss or trigger retargeting. Exercise these states with injected destination results and an offline target-phone trial.

The M9 receipt is a small capture journal, not the M10 processing engine. It records enough to distinguish `capturing`, `settling`, `pending`, and `failed` after restart and to adopt one pending recording into M10 without copying or renaming the only audio file. Give each settlement the same stable recording ID and monotonic state transition so repeated callbacks or reopen cannot mint another job. File completion precedes a pending receipt; a failed receipt-write leaves audio for reconciliation and pauses local work if durable state cannot be written. M10 adds installation identity, worker ordering, readiness, attempts, and restore quarantine. Until M10 is integrated, the UI must describe a durable pending recording without claiming transcription progress.

## Start and stop sequence

1. On `en` or `ko` Record, carry the button's language hint, refresh microphone permission, and inspect the accepted active destination record through M8, distinguishing a temporary provider outage from invalid or known revoked access. Check the approved free-space reserve immediately before allocating the workspace and session. A failed gate has no recording side effect.
2. Allocate a random stable workspace/job identity and persist the independent destination snapshot. Configure the audio session, capture the recording-start instant immediately before the recorder start call, and durably write it with the capture-start marker and protection/backup attributes before accepting audio. Roll back an empty, never-started workspace only after proving it contains no audio; otherwise retain it with a typed repairable state. Do not display a running timer before capture actually starts. Test termination at each persistence and recorder boundary.
3. Drive elapsed display from a monotonic capture clock. Enforce the five-minute maximum independently of a visible timer. Treat Stop & Transcribe, interruption, and time limit as competing requests into one settlement coordinator. Ignore late or duplicate stop callbacks after ownership has transferred.
4. Stop the recorder, close/finalize its file, inspect actual format, bounded byte count and decoded duration, and probe playback/decoding. Distinguish a playable partial from an unreadable one. Keep the file private while validating; never rely solely on the `.m4a` extension or encoder request. Enforce the 64 MiB file limit during capture as well as settlement; avoid buffering the file in RAM. Treat a duration above the approved 301-second asset bound as failed until a bounded, verified correction is possible.
5. Atomically write and verify the settled receipt and its backup/protection attributes. Only then publish a pending or failed state to UI. If protected storage or a write is temporarily unavailable, retain the audio and settlement marker; reconcile after unlock or relaunch without reporting queued prematurely. Keep temporary storage failure distinct from an audio-validation failure, using the approved paused-local-work state for the former.
6. On launch, enumerate only app-owned validated workspaces. Reconcile each marker and audio file with bounded I/O, without assuming a missing read means deletion while protected data is unavailable. Recover a playable partial to pending; retain an unplayable partial or unresolved orphan for review. Reconciliation is idempotent across repeated launches.

The recording target must stay private and backup-excluded throughout capture. Finalized audio may be moved or replaced only within the validated workspace with an atomic, verifiable transition. A failure must leave either the previous file or a recovery artifact. A crash or force quit stops execution; recovery runs on the next launch and must not claim capture continued after process termination. Verify that the selected AAC/MP4 writer leaves a decodable partial under abrupt termination, including termination before container finalization. If it does not, document which partials become failed and bring any proposed mechanism change to the owner before implementation. Diagnostics emit only operation/failure codes, counts, durations, and opaque IDs.

## Audio session and protection trial

Implementation must configure the platform's recording/background capabilities and interruption observation through the Apple adapter, with no new dependency. Treat route changes, phone/audio interruptions, app suspension, and scene state as distinct events; only an actual end/interruption settles capture. Foreground UI disappearance must not itself stop the recorder. Test whether audio-session deactivation or interruption callbacks can occur more than once or after a stop request, and close the recorder only through the settlement owner. The final app capability and audio-session choices are selected from target-phone evidence, while preserving the approved continuous capture and immediate locked settlement.

Use M7's protection-policy seam, then test candidate protection classes on a physical phone for the open audio file, newly created and atomically replaced receipt, closed pending audio, and scratch/recovery files. Verify that lock during capture does not prevent writing and that Stop & Transcribe, interruption, and timeout can close and journal while still locked. Choose the strongest observed policy compatible with those operations; if no candidate meets both immediate settlement and the approved private-storage protection outcome, stop for owner review rather than defer queuing until unlock. Distinguish protected-data unavailability from absent files when reconciling.

The current implementation candidate applies `completeUnlessOpen` to the prepared recorder file and `completeUntilFirstUserAuthentication` to closed audio, snapshots, markers, receipts, and scratch files. Each artifact is also marked backup-excluded and rechecked before a pending receipt is shown. The simulator tests inject a no-op protection policy to exercise journal faults; they do not prove physical lock behavior. Record actual classes and locked access in the [device evidence sheet](milestone-09-recording-capture-recovery-device-evidence.md) before treating this candidate as selected.

## Tests and target-phone scenarios

Use injected clock, authorization, destination, free-space, audio, and private-capture ports for deterministic state and fault tests. Use synthetic speech/noise only; do not put audio content, names, paths, or bookmarks into test logs. Include boundary tests for reserve equality/shortfall, temporary offline destination versus invalid/revoked/wrong-account destination, active-folder change after capture, exact five-minute timer, concurrent stop causes, failed session setup, recorder failure, truncated/unplayable output, 64 MiB plus one byte, receipt replacement failure, protected-data unavailability, and repeated reconciliation. Inspect source dependencies and UI accessibility separately. Run the [required validation gate](../contribution-guide.md#required-validation) after the affected checks.

Record each physical trial with device/OS/build, synthetic input, initial lock and scene state, requested and measured audio settings, stop cause, elapsed time, file/receipt result, observed protection and backup attributes, relaunch result, and a sanitized pass/fail/blocker. Keep account, folder, audio contents, paths, and raw device logs out of the record.

| ID | Target-phone scenario | Required observation |
|---|---|---|
| M9-D01 | Foreground Stop & Transcribe | One playable bounded pending clip and verified receipt; actual audio format recorded. |
| M9-D02 | Tap Stop & Transcribe, then lock before the asynchronous close/receipt completes using a controlled delay | Settlement completes while locked; no extra lock-screen control is introduced. |
| M9-D03 | Background the app without an audio interruption, then return and stop | Capture continuity and correct duration; scene change alone does not settle. |
| M9-D04 | Reach five minutes while locked/backgrounded | Automatic stop and immediate durable pending receipt; no extra capture. |
| M9-D05 | Trigger an audio interruption while locked, then relaunch | Capture ends and a playable partial is durably pending while locked; an unplayable controlled variant is retained as failed. |
| M9-D06 | Kill the process and separately force quit during capture, including before container finalization and between marker/audio/receipt transitions | On next launch, every playable partial recovers once; incomplete/unreadable data remains reviewable. Record which termination points actually leave decodable `.m4a` bytes. |
| M9-D07 | Lock around file close and receipt atomic replacement | Actual protection attributes on audio, receipt, and scratch; no false missing cleanup. |
| M9-D08 | Start near storage-reserve threshold and inject write exhaustion | Low-storage copy is exact; no false queued state; recoverable bytes remain confined. |
| M9-D09 | Relaunch before and after unlock; inspect backup attributes | Reconciliation is idempotent, pending audio is excluded from backup, and inaccessible protected files are retained. |
| M9-D10 | Record offline with a previously accepted folder, then restore provider access | Capture and receipt succeed offline; original destination remains bound and can be revalidated later without automatic retargeting. |

## Downstream handoff

- P1-M10 adopts the capture receipt into its durable queue, creates the `ThisDeviceOnly` installation identity, handles restored-work quarantine, and begins oldest-ready foreground processing only after a valid receipt and audio exist.
- P1-M11/P1-M12 consume the measured playable file and stored language hint through method-specific adapters. They do not infer actual audio format from a filename.
- P1-M14 retains and revalidates the independent original capture destination when publishing the final Markdown/audio pair; P1-M17 gives failed/orphaned capture entries their full retry/removal recovery UI and owns confirmed replacement for a permanently inaccessible destination.
- P1-M18 may acquire optional context from the immutable recording-start event; capture success never waits for it. P1-M19 audits backup/restore and complete-experience races using M9's protection evidence.
