# P1-M16: Diary editing, Favorite, and audio replay approach

Status: Proposal

Extend the read-only detail boundary with version-checked Diary Snippet mutations and leased playback. Keep submitted changes durable, external resources untrusted, and audio-session ownership separate from presentation and capture policy.

## Boundaries and composition

The names below describe proposed responsibilities, not existing APIs. Keep generic catalog routing unchanged; register Diary Snippet actions beside its detail renderer at the composition root.

| Boundary | Responsibility and affected modules |
|---|---|
| Domain | Reuse `DiarySnippetV1`, `DiaryBody`, canonical time/identity rules, and preserved scalars. Construct a revised value containing body/title/provenance together; Favorite changes only its Boolean and update instant. |
| `DiaryEditPort` / application coordinator | Open a fresh version-bound edit session; submit a body or desired Favorite value; serialize one unsettled mutation per resource; return durable acceptance, wait, conflict, validation, or storage outcomes. |
| `DiaryEditJournalPort` | Persist installation-bound transaction intent, candidate/bindings, expected and published versions, proof, recovery, and cleanup checkpoints independently of `QueueJob`. Restore quarantine and idempotent reconciliation follow the private-workspace rules. |
| Coordinated edit adapter | Reuse M7 codec, M8 destination identity checks, and M14 bounded coordination/file observation/upload/snapshot components. Own URLs, security scopes, non-following file operations, expected-version replacement, and platform errors. Add committed-asset entry points rather than invoking capture-only adapters with fake jobs. |
| `DiaryReplayPort` / replay coordinator | Acquire/release an opaque exact-version audio lease and expose media time, playing/paused/loading/unavailable state, seek, and stop. Keep platform player and file handles behind the adapter. |
| Audio-session ownership port | Serialize capture/replay category and activation changes. Adapt `AppleCaptureEnvironment` and the replay adapter to use ownership tokens; only the current owner may deactivate the session. |
| Presentation | Extend M15 detail and `CatalogModel` integration with an editor buffer, explicit submit state, desired Favorite state, replay controls, and typed recovery routes. No direct file writes, codec calls, model calls, or audio-session configuration in views. |

Reconcile the implemented M15 interfaces at M16 entry; M15's device evidence remains open, but its code handoff now exists. `CatalogItemHandle` contains session-local random UUIDs and `DiaryCatalogDetail.audioAvailable` is a read projection. Neither may be serialized as restart authority, expanded into a path capability, or treated as a provider file version. Preserve Clean Architecture's inward dependency rule and type-specific extension model.

## Opening, identity, and lifetime

1. Exchange the selected catalog session/resource/version handle for fresh coordinated validation of both resources. Verify current destination/account identity, supported v1 fields, canonical layout, full audio binding, safe containment, and absence of duplicate claims or unresolved provider versions. A UUID, path, title, or prior successful read cannot authorize a replacement.
2. Inside the adapter, resolve the live catalog capability to a destination-bound stable resource key, expected Markdown/audio provider observations, and content evidence. Return an opaque edit-session reference with resource identity distinct from version, a body revision, and a bounded v1 value. Persist only adapter-owned destination/resource evidence that can be revalidated after launch—never M15's session/resource/version UUIDs, URLs, or bookmarks. Replay instead receives a read-only lease capability. Legacy never receives an edit capability. Unsupported/incomplete/ambiguous items retain their M15 recovery classification.
3. Before submission, active-folder/account changes or a changed source invalidate the session and block writes; preserve the user's visible buffer with a changed/waiting explanation. Reopening the new version is explicit, never a silent replacement of the editor's text.
4. A submitted operation becomes accepted only after its candidate and binding journal are durably verified. It then owns a separate destination loan pinned to the original folder/resource. Catalog refresh, navigation, or a later active-folder choice cannot retarget it or erase its journal. New-folder UI receives no former-folder content from a late callback. Account identity changes suspend access and require revalidation against the bound identity; no automatic cross-account publication is allowed.
5. Fence callbacks by transaction, destination/account binding, resource, expected pair revision, editor/body revision, and player generation as applicable. Cancel superseded work and wait for accessors to relinquish before releasing scopes or granting another mutation for that resource. A deadline invalidates results but is not proof of settlement. Keep stalled work truthfully waiting and do not start unlimited replacement attempts.

## Body and Favorite operations

`Edit Diary` contains one multiline plain-text body field and explicit Save/Cancel actions. Preserve selection/focus and Korean marked-text composition across view updates; perform UTF-8 limit validation without truncating or rejecting partial input-method composition. Show a useful inline error for a body beyond 1 MiB and keep the buffer. Empty text is valid. Keep Save reachable above the keyboard with Dynamic Type and accessibility sizes. Leaving a dirty buffer asks to keep editing or discard; this does not discard an already accepted save. No per-keystroke persistence or recovery guarantee before Save is introduced.

On Save, snapshot the exact submitted body revision and persist it before starting title generation. Reuse `DiaryTitlePolicy` and the [approved title contract](milestone-05-decisions-architecture.md#title-contract): current body language, bounded all-part coverage, 30-second budget, first-sentence fallback, 30 Swift grapheme clusters including ellipsis, and `Untitled`/`empty-body` for an empty trimmed body. Use a provisional fallback in private staging if necessary; persist and verify the finalized candidate before any external write. Do not persist model intermediates as another transcript. Remove obsolete AI-only provenance fields when falling back. A timed-out or superseded model result cannot rewrite that candidate later; a readiness change alone never regenerates a saved title.

Build the revised Markdown through the existing codec. Preserve identity, kind/schema, `created_at`, UTC paths, recording language and hint, recording/audio properties, audio filename/digest, transcription provenance, optional context, and unknown flat scalar values. Preserve malformed optional-group scalars on an unrelated rewrite without displaying/interpreting them. Do not backfill location/weather or infer new recording metadata from edited language. Capture one canonical whole-second `updated_at` for the proposed saved revision before publication: use the current canonical second when it is later than the source value, otherwise use the source value plus one second. Reuse that value on retries; it is not a concurrency token or conflict tie-breaker. An unpublished/failed intent changes no external timestamp.

Favorite submits `setFavorite(desiredValue, expectedVersion)`, never an unqualified toggle. Preserve body, title, and all title provenance and skip the title model. If the freshly verified value already equals the desired value, return confirmed without an external rewrite or `updated_at` change. Coalesce repeated taps before acceptance and disable resubmission while that transaction is unsettled; the confirmed value follows verified publication, with waiting/failure visible. A retry of the same transaction is idempotent. Serialize body and Favorite writes for one resource; while its editor is open or its save is unsettled, do not accept a separate Favorite mutation that would invalidate the editor's base. A Favorite write from another session is an external version change, not permission to overwrite it. Different resources do not share a global edit barrier.

## Durable submitted-edit journal

Use a bounded versioned private transaction record, not the transcription queue record. Store a random transaction ID, installation binding, kind/asset identity, source resource/destination reference, expected pair versions and content evidence, candidate revision and Markdown digest/length, verified source-audio snapshot reference/digest/length, title/candidate stage, publication evidence, observed uploads, recovery status, and cleanup progress. Opaque references resolve only inside confined adapters. Do not store a caller-supplied deletion path. There is no count cap on retained pending work; use one active mutation and bounded buffers, not a full in-memory body/audio cache per retained transaction.

The submitted candidate and the exact source audio form a recoverable complete pair. Capture the audio into protected, backup-excluded local staging with bounded streaming and source-version checks before publication; do not depend on a mutable external audio URL after the user submits. This is temporary transaction/conflict staging, not an enduring original transcript or edit-history feature. Do not rewrite the external audio for a normal body/Favorite edit. A disk-full, locked-file, candidate/binding mismatch, or journal-write failure retains prior valid state and reports no false durable acceptance. Partial private artifacts are reconciled by positive ownership and bindings.

Reopen validates each record and candidate independently and rebuilds same-resource mutation claims from the journal's destination/resource evidence before accepting new writes. A submitted body awaiting title can rerun the bounded title stage or finalize its fallback; a finalized candidate does not change title on retry. Missing/malformed records are isolated with sanitized diagnostics and cannot block valid transactions, queue work, catalog refresh, or replay, nor authorize external repair. An unavailable installation identity/protected store waits; a mismatched installation binding quarantines restored edits for M17 review before title work, publication, or cleanup. Do not silently reuse the restored folder reference. M16 produces the typed review state without adding a new recovery destination. Bound reconciliation work so multiple retained transactions cannot create an unbounded launch scan or concurrent provider storm; no recording-queue ordering rule is reused or invented for edits.

## Checked publication, proof, and cleanup

1. Acquire the resource mutation barrier and revalidate the pinned destination loan, current full pair, and both expected versions. Keep the journal and verified local candidate/audio intact. Ordinary iCloud failures wait; only the original exact resource may be resumed, with no automatic new-folder save.
2. Persist finalized intent before writing. In coordinated access, check both source versions and unresolved-conflict state again at the replacement point. Replace only Markdown atomically using a provider-supported checked operation; external audio stays byte-for-byte unchanged. Coordination is not a cross-device lock: recheck after replacement and route later conflicts to recovery. Bind the replacement to positive transaction evidence, extending M14's creation/checkpoint evidence for replacement where the provider supports it. Never overwrite an unexpected resource because its ID or contents happen to match.
3. Reopen and validate edited Markdown against the candidate and referenced audio against its exact expected source. Verify layout, all bytes/digests, safe containment, and stable identities/conflict state. Persist the new pair version. Refresh catalog/detail from this observation; distinguish locally published changes from upload verification still pending.
4. Observe successful upload independently for this Markdown version and the unchanged audio version. Reuse an audio report only if it still proves that exact version under the same validated destination/account binding. Recheck both files immediately before durable completion. Missing or changed proof keeps the candidate waiting; connectivity, local readability, and elapsed time are not upload proof.
5. Durably record completion, then remove only positively owned private candidate/audio/snapshots and journal resources. Cleanup interruption resumes cleanup without another external write. If the journal cannot persist proof, retain staging and reverify. Once cleanup completes, later outages cannot depend on a private backup of the finished asset.

On crash after replacement but before checkpoint, adopt the result only with positive identity/version and transaction-write evidence plus expected contents. If the provider cannot preserve trustworthy evidence, retain the candidate and return recovery rather than overwrite or discard it. Candidate-byte equality or a copied marker is insufficient authority. On retry, distinguish a verified own publication from a subsequent external edit. A complete later external revision does not justify throwing away an unverified local edit.

Use M14's bounded asynchronous coordination and upload observations with committed-asset bindings. Provider wait expiry releases the active barrier only after accessors settle and a durable waiting checkpoint exists; fresh retries start by verifying the whole pair. The target-phone upload and replacement-evidence gaps inherited from M14 remain explicit gates, not assumptions satisfied by unit tests.

## Conflicts and M17 handoff

An expected-version failure preserves the submitted candidate and validated external version separately; do not merge bodies, replay the edit on a newer base, or assign iCloud time to an unpublished candidate. Return a typed conflict record binding resource/destination, candidate snapshot references, observed pair versions/times, safe read-only availability, and the existing Conflicting Versions route. Invalid or unpairable external content uses Incomplete Diary Snippets; temporary access loss stays waiting. Pending submitted edits remain distinguishable from pending recordings in the inward model even when M17 presents their recovery.

For actual provider conflicts, reuse the approved whole-pair policy only after each complete pair validates. Two Markdown versions can each reference one uniquely validated unchanged audio version; retain independently verified complete snapshots without inventing a second audio version. Multiple indistinguishable audio matches remain ambiguous. Shared audio modification times do not satisfy the policy's strict later-both-resources test, so text-only conflicts require M17 choice. Never bump audio timestamps or use front-matter `updated_at` to force a winner.

Chosen-pair publication, separate upload reports, final verification, and obsolete-version cleanup follow M14. Equal/missing/cross-ordered times or an unpublished local candidate require explicit choice; M17 owns that presentation and confirmation before removing the unchosen version. Unknown/shared resources remain preserved. M16 neither deletes a finished asset nor adds an alternate conflict UI while M17 is pending.

## Replay lease and media state

Opening detail does not auto-play. Play acquires a new read-only lease from the exact observed v1 or eligible legacy pair. Revalidate destination/account, pair versions, confinement, no unresolved conflicts, actual format/bytes/digest, and clean decoder EOF. Apply the existing 64 MiB audio limit, 301-second v1 decoded-duration limit, and 60-minute legacy limit. Use frame/duration evidence, not declared metadata or rounded UI time. A transient provider wait remains retryable; legacy with unavailable audio keeps safe text readable. No lease is returned for unsafe, ambiguous, or unsupported content.

The adapter streams a stable compressed-audio snapshot into one protected, backup-excluded private replay cache and verifies its binding before exposing an opaque lease. When private-volume capacity is available, preflight at least the bounded audio byte count; this is admission evidence, not a new fixed reserve policy. Insufficient capacity or a partial-copy/write failure returns typed unavailability and cleans only positively owned partial cache data. Unavailable capacity telemetry permits only the same bounded streaming attempt and can never turn a failed write into success. Source checks bracket the coordinated copy; replacement or growth invalidates acquisition. Use bounded byte buffers and incremental decoding off the main actor, never whole-file PCM or allocations derived from untrusted duration. Reuse M15's measured decode/cancellation budgets so a valid 60-minute legacy file is not rejected by an arbitrary short provider timeout. A cache is disposable on reopen, never treated as a pending job or a source for external repair. Release/delete it only after player/decoder access relinquishes; reconcile owned abandoned caches without touching source files.

Expose loading, ready/paused, playing, seeking, ended, and typed unavailable states as value projections. Play/pause does not re-create the player or restart from zero; seeking clamps to the verified media duration, coalesces rapid requests, and fences completion by lease/player generation. End-of-audio returns to a Play action; Play from the end starts at zero. Elapsed/total time comes from the player and verified media, not recording metadata. Cancel timers, observers, pending seeks, and acquisition work on detail close, nonforeground transition, folder/account invalidation, or lease invalidation. Stop replay and require a new explicit Play after reentry; add no background playback capability.

`Play audio` and `Pause audio` are action labels. `Audio position` exposes `{elapsed} of {total}`, supports direct seeking, and has accessible increment/decrement actions of 15 seconds, clamped at either end. Keep elapsed-time updates available without repeated VoiceOver announcements. Use native adjustable-control semantics so dragging is not the sole seek interaction. Optional play/pause/seek artwork follows the approved template bitmap system; do not replace it with the UI skill's generic vector preference.

## Capture and session arbitration

Capture and replay share one adapter-owned audio-session arbiter with separate coordinators. Capture has priority: a Record attempt stops replay, waits for its player/session lease to settle, then configures recording. If replay cannot relinquish, report unavailable rather than configure two owners or pretend capture started. Play during capture is unavailable and cannot pause, stop, reconfigure, or deactivate recording. Replay teardown checks its ownership token; a late callback cannot deactivate the newer recording owner.

Pause replay on system interruption and output-route loss; route changes must not unexpectedly move private audio to the speaker. Require explicit Play to resume after interruption/capture. Handle denied activation, media-services reset, decoder failure, and disconnected headphones as typed states with settled cleanup. Playback acquires no microphone permission. Preserve M9's lock/background recording, interruption settlement, five-minute stop, playable partial recovery, and queue handoff. Audit other audio-session users before integrating the arbiter; file inference must not seize capture/replay ownership accidentally.

## Presentation and privacy

Keep `Diary Snippet` layout as Title with Favorite, inert body with its editor entry, then bottom Metadata containing replay and read-only recording details. Legacy has no editor or Favorite action. Title provenance stays hidden, stored weather keeps attribution, unavailable context stays omitted, and edited text cannot create interactive links/HTML/remote fetches. No new toolbar or root destination is introduced.

Use monochrome custom template Favorite/play/pause/seek state art at 1x/2x/3x and 24 pt inside at least 44-by-44-point targets. Expose Favorite's selected value and disabled/waiting state independently of color. Keep keyboard and safe-area insets, focus order, labels, contrast, largest Dynamic Type, landscape, and Reduce Motion usable. Preserve normal accessibility reading of visible diary content without putting content into accessibility identifiers or diagnostics. The neutral privacy cover must include editor buffers and replay UI before nonforeground snapshots. Evidence/logs contain only sanitized operation/state codes, counts, duration/size classes, and opaque IDs.
