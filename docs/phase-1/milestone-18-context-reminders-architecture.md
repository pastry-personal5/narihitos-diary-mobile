# P1-M18: Optional context and pending-work reminders approach

Status: Proposal

Revised 2026-11-11: M18a (reminder) is implemented and verified before M18b (context); weather uses Open-Meteo instead of WeatherKit; manual snippets receive context at first Save; waiting manual saves are reminder-eligible; the pending observation is built over existing owners because M17's unified inventory was cut. See the overview's owner decisions.

Bind context to the successful recording-start event and reminders to durable unfinished work plus actual app departure. Keep both optional effects outside capture/inference ownership, and serialize their late results with the existing draft, commit, removal, and lifecycle generations.

## Existing seams and proposed boundaries

Responsibility names below describe proposed interfaces. Reconcile the actual M16/M17 implementation at entry; do not treat a planned handoff as an existing API.

| Boundary | Responsibility and integration |
|---|---|
| Recording-context coordinator/ports | Consume immutable `CaptureIdentity` after successful `CaptureCoordinator.start`, check preference/authorization, own a cancellable acquisition generation, validate plain location/weather values, and expose an immediate snapshot/seal operation. |
| Context store | Bind one bounded record to capture ID, start instant, installation, preference epoch, and context revision. Reuse confined private workspace/protection/backup-exclusion mechanisms; no caller-supplied file path becomes authority. |
| Draft/publication integration | Replace `DiaryDraftFactory`'s unconditional nil groups with a verified snapshot. Extend draft bindings and M14 commit checks as needed to serialize sealing/revocation with the exact serialized Markdown; preserve stable asset/body/title/audio identity and provenance. |
| Context adapters | Core Location for a short foreground acquisition, MapKit for reverse geocoding, and an `URLSession` Open-Meteo adapter behind a `WeatherPort` for current conditions (HTTPS, host allowlist, size/time limits, strict decoding, WMO code to fixed English summary). Translate to bounded plain values and typed omission reasons; own cancellation and resource release. |
| Context preference | Extend the existing private Settings store with backward-compatible decoding and explicit write outcomes. Reuse live `LocationAuthorizationPort`; publish preference/authorization invalidation events to the context and publication owners. |
| Pending-work observation | Consume a narrow M18a-owned projection over the existing capture receipt, queue job, M16 accepted-edit and M21 manual-submission owners, deduplicated by owner ID,, with a monotonic revision and `present`, `empty`, or `unknown` result. Lists/notices and reminders share state semantics without sharing sensitive row contents. |
| Reminder coordinator/store | Own one departure generation, permission-attempt guard, desired schedule, installation binding, and reconciliation checkpoints. Depend on injected time/calendar, app lifecycle, pending observation, authorization, and scheduler ports. |
| Notification adapter/composition | Own `UNUserNotificationCenter`, live settings, one stable request identifier, calendar trigger verification, pending/delivered cancellation, and generic All navigation. Composition supplies real app/scene transitions independently of Settings/view refresh. |

Domain/Application must not import CoreLocation, MapKit, URLSession, UserNotifications, UIKit, or provider/persistence APIs. New adapters use system frameworks already allowed by the architecture; no package/runtime/build-tool change is part of this milestone.

## Platform evidence and configuration

Apple documentation checked on 2026-11-02 supports these mechanisms; this is API evidence, not target-phone acceptance:

- Core Location supports a [single location request and stopping services promptly](https://developer.apple.com/documentation/corelocation/getting-the-current-location-of-a-device). A [negative horizontal accuracy is invalid](https://developer.apple.com/documentation/corelocation/cllocation/horizontalaccuracy); [reduced authorization](https://developer.apple.com/documentation/corelocation/cllocationmanager/accuracyauthorization) cannot be overridden by `desiredAccuracy`. Use When In Use only and leave background location disabled.
- Apple's [MapKit geocoding guidance](https://developer.apple.com/videos/play/wwdc2025/204/) replaces deprecated `CLGeocoder` with `MKReverseGeocodingRequest`. Keep the geocoder behind its own port; request only a place label for the accepted coordinates, with no map/search UI or additional location capability.
- Open-Meteo: see [Open-Meteo terms verified 2026-11-11](#open-meteo-terms-verified-2026-11-11). No WeatherKit entitlement, account capability or profile change is part of this milestone.
- Replace M15's Apple Weather attribution presentation with the Open-Meteo attribution text and link beside displayed weather; its current adapter retrieves Apple attribution only and proves no lookup capability.
- Apple recommends [contextual notification authorization and checking live settings](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications). [Calendar triggers](https://developer.apple.com/documentation/usernotifications/uncalendarnotificationtrigger) expose `nextTriggerDate()`, and [local requests remain scheduled until triggered or explicitly cancelled](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app). [Calendar matching](https://developer.apple.com/documentation/foundation/calendar/nextdate(after:matching:matchingpolicy:repeatedtimepolicy:direction:)) supports explicit missing/repeated-time policies. Test the adapter's actual calculated trigger; fixed 86,400-second arithmetic does not implement a local calendar day.

## Recording-start context lifecycle

1. After audio starts, deliver the same immutable recording ID/start instant/installation binding persisted by M9. Start acquisition independently; no context error may roll back or delay successful capture. On failed start, cancel any prepared context work and retain no fabricated recording metadata. Never use the Record tap, transcription start, retry time, or draft time as the context instant.
2. Check the app preference, live authorization, and location-services availability without requesting permission. M8 still owns first-launch explanation/request and explicit Settings recovery. An absent preference in older settings inherits permission-based opt-in; it grants no system permission. Persisted Off remains Off. Reduced accuracy is acceptable only when the returned sample meets the same approved accuracy threshold; do not request temporary full accuracy.
3. Use one cancellable acquisition per recording. Proposed implementation budgets are 15 seconds for location and at most 15 further seconds for concurrent place/weather requests, with a 30-second overall monotonic deadline from capture start. These are work limits, not save delays. Stop acquisition earlier on valid completion, initial snapshot sealing, actual background departure, opt-out/revocation, failed capture, removal, or supersession. A new recording may start without waiting for an old SDK callback; bound outstanding adapter work and omit new optional work if an old operation has not relinquished resources.
4. A location sample needs finite latitude/longitude in the schema ranges, nonnegative finite accuracy at most 500 m, and a genuine sample timestamp. Reject a timestamp older than `recordingStart - 300 seconds`, older than five minutes at acceptance, or later than the current callback time. A fresh fix delivered during the short start-acquisition window is eligible; do not continue tracking throughout a five-minute recording. Validate full-precision times before canonical whole-second serialization, including exact/just-outside boundaries and clock changes. Save the returned coordinates without intentional rounding or replacing them with a map item's coordinates.
5. Once a location is accepted, immediately retain its complete typed group and request place/weather concurrently within the remaining budget. Place lookup may add only a nonempty bounded label; failure leaves coordinates. Weather requires a nonempty bounded summary, finite Celsius temperature, and `abs(weatherDate - recordingStart) <= 3,600 seconds`. Check the data date rather than request/receipt time; never fetch historical weather later to fill a missed recording. Missing location means no place/weather request. Failure of either lookup does not erase the other accepted group.
6. Before each outbound lookup and acceptance, recheck authorization/preference and operation epoch. The adapters receive only accepted coordinates and necessary start-time/locale inputs, never audio, diary/title/prompt text, destination capability, or another recording's context. Do not share a persistent coordinate/result cache across recordings or restart lookup on reopen, transcription Retry, Resume, destination replacement, edit, or catalog read. Late/out-of-generation results are discarded even if task cancellation was ignored.

The budgets are tunable implementation mechanisms only while acquisition remains bounded, recording-start scoped, and nonblocking. Do not relax the approved five-minute/500 m or 60-minute acceptance rules without owner approval. On background/lock, stop new context work and accept no further callbacks; preserve already accepted values while M9 capture continues and settles durably.

## Open-Meteo terms verified 2026-11-11

The full [research record](milestone-18-open-meteo-research.md) separates page statements from inferences. Read from Open-Meteo's [terms](https://open-meteo.com/en/terms), [pricing](https://open-meteo.com/en/pricing), [docs](https://open-meteo.com/en/docs) and [licence](https://open-meteo.com/en/licence) pages. Pages may change at any time without notice; re-check before release.

- **Use:** free API for non-commercial use only. Listed as non-commercial: private or non-profit apps without subscriptions or advertising. Listed as commercial: apps with subscriptions or ads, and commercial products or promotion. App Store distribution is not addressed; written confirmation is available from the contact address on the site.
- **Limits:** under 10,000 calls/day, 5,000/hour and 600/minute (the pricing table adds 300,000/month), applied per IP address and application. One request is normally one call; more than 10 variables or a long date range counts as several. Request exactly two variables. Shared carrier IPs could hit limits earlier, so treat HTTP 429 as an omission with no retry loop. Blocking without notice is reserved.
- **Key:** none for the free `api.open-meteo.com` endpoint.
- **Attribution (CC BY 4.0):** credit, a link to the licence, and an indication of changes; "a link next to any location Open-Meteo data are displayed", for example "Weather data by Open-Meteo.com" linking to `https://open-meteo.com/`. Show this beside displayed weather in Metadata.
- **Privacy:** IP addresses may be collected for server maintenance and misuse prevention; web-server logs may contain coordinates, are not shared with third parties, and are deleted after 90 days. The Settings disclosure must say so.
- **Reliability:** no uptime guarantee and no warranty; data is provided as is.
- **Request and parsing:** `current=temperature_2m,weather_code&timeformat=unixtime`, with the default GMT timezone. Use the unix `current.time` as the validity instant: the default ISO format is a local time without an offset, which would make the 60-minute check ambiguous. Open-Meteo says `current` is derived from 15-minute weather model data, not station observations, and its refresh cadence is not stated. Validate `current.time` against the start instant; the stored `weather_observed_at` records that model validity time, and Metadata must not imply a station reading.
- **Summary text:** map WMO `weather_code` through a fixed in-app table to English summaries (0 Clear sky, 1 Mainly clear, 2 Partly cloudy, 3 Overcast, 45 Fog, 48 Depositing rime fog, 51/53/55 Light/Moderate/Dense drizzle, 56/57 Freezing drizzle, 61/63/65 Slight/Moderate/Heavy rain, 66/67 Freezing rain, 71/73/75 Slight/Moderate/Heavy snowfall, 77 Snow grains, 80/81/82 Rain showers, 85/86 Snow showers, 95 Thunderstorm, 96/99 Thunderstorm with hail, 97 Heavy thunderstorm). Unknown codes omit weather. Codes 96 and 99 appear only for models with a hail forecast.

## Weather lookup and manual-snippet context

The weather toggle (default Off) and the location preference are both checked before the request and before accepting a result. The adapter sends only coordinates rounded to two decimals and the two requested variables, over HTTPS to the fixed Open-Meteo host, which also sees the device's IP address; the stored location group keeps the exact returned coordinates. A failed, throttled, malformed or oversized response omits weather without retry loops. Requests are one per recording or manual first Save, with no shared cache.

For a manual snippet, the first Save is the context instant. Begin the same bounded acquisition then; the Save acknowledgment, protected local acceptance and dismissal never wait for it. Freeze available context at first publication, with the same sealing, revocation and cleanup rules as recordings, bound to the manual submission's journal instead of a capture ID. Extend the schema 2 manual codec to allow the typed location/weather groups only for explicit manual snippets, and keep rejecting them where the existing codec forbids them.

## Private context and initial publication

Use a versioned context envelope with an opaque workspace identity, installation/start binding, operation/preference epochs, validated groups, and collecting/sealed/omitted state. Limit it to 32 KiB and each scalar to the existing 8 KiB limit, respecting the 64 KiB front-matter budget. Store only recognized typed values, not platform archives, map-item identifiers, SDK errors, URLs, request histories, or caller-controlled paths. Confine access and apply/verify backup exclusion and the capture workspace's lock-compatible protection to replacements as well as original records. Do not weaken existing Data Protection to accommodate context.

Persist accepted coordinates before optional enrichment when storage is available. An optional-context write failure omits unpersisted values and must not turn a valid capture into a failed job. Protected-data unavailability is distinct from absence: do not delete another record or report cleanup success. Validate the envelope's exact recording/start/installation ownership on adoption; malformed or substituted context is ignored as optional input while the owning recording retains its existing recovery rules. Old jobs have no context; restored/unbound records cannot authorize new lookups or bypass M10/M17 review. After review, reuse only positively bound previously accepted data, never the device's new location.

At the first draft construction, synchronously seal the available validated snapshot without awaiting acquisition. Persist a revision/digest binding with the draft record before transitioning the job. Once sealed, reject all later enrichment, even if the destination is offline for days. Reopen reconciles envelope/draft checkpoints without rebuilding from unverified bytes. If context storage is missing or invalid, use complete available groups or omission; never synthesize zero coordinates, placeholder weather, or a new context timestamp. If an already verified context-bearing draft is the remaining recovery copy, retain it rather than discarding it because its optional envelope was lost.

Revocation/opt-out and publication share the existing job mutation barrier with removal, retry, draft adoption, retargeting, and M14 saves. Invalidate acquisition epochs immediately. Before the first metadata-bearing coordinated write, recheck permission/preference and the sealed revision. If revocation wins, remove unpublished location/weather from the private candidate, durably rebind its Markdown digest and draft/commit checkpoints, and proceed without context; retain body/title/audio and stable asset/timestamp values. An old commit record cannot later publish the revoked candidate. A crash between these steps must converge to the same omission before publication.

If metadata was already written while authorized, do not silently edit that published asset in response to later permission changes. Fence further stale metadata writes and let M14 reconcile the exact partially published files and upload proof; an audio-only write does not authorize a stale Markdown write. Never infer replacement/deletion authority from matching asset IDs or regenerate bytes underneath an active accessor. If the existing writer cannot settle or positively rebind an unverified publication, retain recovery state until it can; do not promise retroactive withdrawal of data already sent to a provider. Device races must establish this boundary without weakening the approved opt-out outcome.

Retain the owning context record through safe draft binding and required recovery. M14 verified completion and M17 confirmed removal clean positively owned context staging along with the job's other private copies; crash cleanup remains idempotent. Saved metadata is preserved by M16 body/Favorite edits, and no sync/read changes `updated_at`. Unknown/malformed optional fields in externally edited assets retain the codec's existing preservation behavior; acquisition does not reinterpret or repair them.

## Pending-work eligibility and navigation

Observe durable owner state independently of Main/All visibility, active-folder scans, or row counts. Eligible work includes unadopted playable pending capture receipts and jobs in ready, transcribing, result-ready, ready-to-save, prerequisite/save/upload waiting, review-required, and cancelling/removing stages. Include M16's durably accepted edits awaiting publication/upload/review, including an owning job/edit awaiting conflict resolution. Deduplicate receipts adopted into jobs and preserve original-folder work after active-folder changes. An ongoing capture becomes eligible when it settles durably; retain the departure anchor so settlement while locked can schedule correctly.

Waiting manual saves (Pending Diary Snippets) are eligible and cleared by verified upload, confirmed removal or purge. Failed-only recordings, isolated unreadable/malformed recovery issues, unsubmitted editor buffers, standalone external incomplete/conflict assets, active model downloads without a job, and empty catalog pages do not independently create a pending reminder. A manual Retry/Resume re-enters eligibility through its owner's state machine. This uses the distinction between Pending Recordings and Failed/Incomplete/Conflict recovery already established by M17; a bound unfinished transaction remains eligible even when its action is presented in a conflict screen.

Use `present`, `empty`, and `unknown` with an observation revision. `empty` requires settled authoritative capture/queue/edit observations; unavailable protected storage or partial reconciliation is `unknown`, not zero. Unknown state cannot create a new reminder from an unproven count or clear a previously justified request as if work finished. Retain the last valid desired state until reconciliation, with no growing retry loop. Notification text and payload contain no count, title, location, language, folder name, or resource ID. Use the exact body `You have pending diary work.` and a fixed opaque All route; add no content attachments, badge, custom sound, or action that mutates work. A tap activates the normal privacy/lifecycle flow, opens All, and rechecks current state; stale notifications grant no action authority.

## Reminder permission and lifecycle

Request alert authorization only once a durable eligible item makes a future reminder necessary. If foreground and not capturing, explain the pending-work purpose in its existing recovery context and persist a request-attempt marker before calling the OS. A permission sheet's inactive transition is not departure. If first need arises during capture/background, defer prompting until the next safe foreground opportunity; existing authorization can still schedule after locked settlement. Do not wait for permission before preserving/processing the job. Request no provisional authorization, sound, badge, APNs entitlement, or background task capability for this feature.

Read live notification settings before scheduling and on reopen/Settings recovery. A stored attempted marker never represents granted permission. Denial or disabled alerts keeps in-app state and a nonblocking Open Settings action in the pending context/existing Settings screen; do not repeatedly call authorization or show repeat nag dialogs. A crash after the attempt marker but before the OS call suppresses automatic repetition, with explicit recovery available when the OS still allows a request. Concurrent permission requests coalesce; completion after work clears or a departure changes cannot recreate old desired state. Preserve existing location/microphone first-launch behavior.

Use a single application lifecycle owner, distinct from view appearance and the current general-purpose `becameActive()` refresh. Record one actual foreground-to-background departure with its instant and local hour/minute/second; transient inactive states from permission sheets, pickers, Control Center, or interruptions do not schedule or move the anchor. Keep the nonforeground privacy cover active throughout. Repeated background events and background capture settlement reuse this anchor. No reliable termination callback is assumed.

For each departure with eligible work and usable authorization:

1. Persist an installation-bound departure generation and desired reminder before the scheduling side effect. Snapshot the current local calendar/timezone, take the local date containing the departure instant, advance by one calendar day, and apply the departure's wall-clock hour/minute/second. Use next-valid-time matching for a missing DST time and the first occurrence for a repeated time. Handle calendar/year/date boundaries and skipped local dates without adding a fixed number of seconds.
2. Create one nonrepeating calendar trigger with explicit date/calendar/timezone components. Compare `nextTriggerDate()` with the computed future instant before adding. Nil, past, or mismatched dates yield a typed scheduling failure with in-app recovery intact, not an immediate notification or a silent fallback interval.
3. Serialize add, replace, cancel, and pending/delivered inspection for one stable app-owned identifier. Check the desired generation after every await. If an old add completes after clear/reopen/replacement, remove it or converge to the newest desired request; a stale cancel must not erase a newer schedule. Persist/reconcile intent and OS observations so a crash between add and checkpoint neither duplicates requests nor treats absence as delivery proof.
4. On reopen, refresh authorization and pending owners, then reconcile the prior departure in the current timezone/calendar while preserving its stored wall time. Recalculate the following local date from that departure instant; do not create a new departure from view refresh. Replace a still-future request if needed. Retire an overdue request rather than firing it immediately or making a recurring daily schedule; the next genuine departure creates the next one-shot reminder. A clock/timezone change while suspended cannot be guaranteed to run app code; reconcile on the next available lifecycle event.
5. As soon as all eligible work is authoritatively empty, cancel the pending request and remove a stale delivered reminder for the owned identifier. Recheck after upload completion, removal, retry, review, edit settlement, and background capture events. Suppress foreground notification presentation and use the existing in-app state. If the process is suspended/killed, no new processing is promised; reconcile completion observed later on reopen rather than claiming a guaranteed background cancellation.

Retain only a small bounded reminder record (installation binding, permission-attempt flag, departure/wall-time/calendar values, generation, desired trigger/checkpoints). It contains no job content or identifiers and no coordinate cache. Validate older/restored state, never replay a prior installation's schedule from a persisted intent alone, and rederive eligibility after review/reconciliation. Scheduling failures stay separate from queue failures and never prevent capture or saving. No callback or timer is needed at delivery for correctness.
