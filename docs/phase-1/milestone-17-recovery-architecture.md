# P1-M17: Pending, failed, incomplete, and conflict recovery approach

Status: Proposal

Connect recovery presentation to typed, durable owner-specific operations. Treat discovery, safe inspection, action authorization, publication proof, and cleanup as separate steps so a stale view cannot overwrite or delete another revision.

## Boundaries and existing handoffs

The responsibility names below are proposed interfaces, not claims that these APIs exist. Reconcile the actual M15/M16 implementations at entry; retain Clean Architecture's inward dependency rule and registered asset-specific adapters.

| Boundary | Responsibility and integration |
|---|---|
| Recovery inventory port/coordinator | Merge lightweight queue, capture-recovery, catalog, and submitted-edit projections. Expose opaque owner/resource/version handles, typed reasons, available intents, continuation, and invalidation events. Keep bodies/audio out of list projections. |
| Recording recovery use cases | Extend `ProcessingQueueCoordinator` with distinct retry, restored Resume, verification/access retry, removal, and per-job retarget intents. Reuse M10 claims, M13 drafts, and M14 commit records/barriers rather than resetting every wait to inference. |
| Asset-specific recovery port | Exchange an observed M15 handle for fresh bounded surviving-content inspection, exact-resource removal authority, or complete conflict snapshots. Reuse `DiaryRecoveryInspectionPort`, `DiaryExternalPairClassifier`, codec, confined file access, and bounded coordination. Add committed-resource bindings beside capture-specific methods. |
| Recovery journal and conflict coordinator | Persist confirmation-bound cleanup intent, selected candidates, expected/published versions, upload proof, and settlement/checkpoint state. Reuse M14 mechanisms with capture, committed-resource, or M16 edit ownership; never create a fake `QueueJob`. |
| Destination selection adapter | Use M8 positive iCloud/account validation and transactional bookmark persistence for a per-job replacement. Keep picker URLs, security scopes, stored references, and provider failures inside adapters. Selection for recovery must not replace Settings' active-folder record as a side effect. |
| Read-only recovery/replay adapter | Lease freshly checked surviving audio or protected snapshot audio through M16's player/session arbiter. Own platform players, private copies, decoding, and release. Recovery never grants edit/Favorite authority. |
| Presentation/composition | Replace minimal `CaptureListView` actions and `CatalogRecoveryAttentionView` placeholders with four All screens and their read-only previews/dialogs. Extend `AppModel`/catalog integration using typed intents; register Diary Snippet recovery beside its catalog/edit handlers. |

Current `QueueProjection.reason` and catalog `hasText`/`hasAudio` flags are display observations. They do not grant action, read, playback, or deletion authority. `DiaryCommitCoordinator.chooseConflict` and `confirmConflictRemoval` are capture-owned starting points; strengthen their confirmation binding rather than invoking cleanup with only the current job ID. M16's planned shared-audio conflict support must also be present before using these mechanics for text-only edits.

## Inventory, scope, and navigation

Use an opaque owner key distinguishing a recording job, unadopted capture/recovery issue, committed external resource, and submitted edit. Keep resource identity separate from observed version and external asset ID. Adopted receipts project once through the queue; malformed/unadopted captures remain individually reviewable with their source owner. A duplicate external ID never deduplicates distinct resources. Correlate a catalog issue and an owning transaction only through positive resource/destination bindings, retaining both owners' evidence without presenting duplicate actions.

Recordings and accepted edits remain visible across active-folder changes through their pinned original destinations. External incomplete/conflict discovery is restricted to the active folder. Show these scopes clearly in the existing destinations; submitted diary edits have a distinct section and never masquerade as new recordings or offer transcription Retry. Their ordinary waiting/review state uses Pending Recordings; complete conflicts use Conflicting Versions; malformed external counterparts use Incomplete Diary Snippets. Reuse M16's edit-specific retry/review semantics, preserving accepted text; this does not authorize deletion of the finished asset or introduce an edit-discard feature.

All must start or resume recovery discovery without requiring a prior Main visit or scroll. Reuse M15's catalog discovery infrastructure with an explicit consumer/session lifetime so navigation away from Main does not cancel All's inventory or retain an obsolete active-folder session. Use cancellable slices and at most 50 catalog candidates per page, lightweight retained summaries, and on-demand bodies/snapshots. There is no total collection or pending-work count cap. Recovery-only pages and unrelated-file slices advance continuation; a partial scan is not an empty folder, and counts are observed counts until discovery settles. Distinguish loading, continuation, no folder, temporary access loss, isolated issue, storage pause, and verified empty/end states. Do not run two unbounded folder scans or decode every retained audio file to draw a count.

Project the same typed state into All destinations, Main notices, and M18's pending-work observation. Keep the four exact destination headings and Settings entry under All. Main queued/processing notices open Pending Recordings; recovery notices open the relevant destination without copying rows into Main. Returning to a stale route reopens/revalidates its owner/version; a completed/removed item yields a truthful outcome instead of acting on a replacement row. Folder/account invalidation clears external previews and confirmation authority immediately; late callbacks cannot insert old-folder content into the current catalog.

## Pending and failed actions

Use enums for recovery stage/reason and typed capabilities returned by the owning application use case. Map approved messages/actions at the presentation boundary. Preserve P1-M5 wording; only validated, bounded display language/folder values may fill its placeholders, never raw errors or paths.

| Condition | Presentation and intent |
|---|---|
| Apple locale not ready | `Apple transcription isn’t ready for {language}.` with `Download Model` / `Choose Method`, where supported. Installation delegates to M11 and shows truthful progress/reason. |
| Cohere missing | `Cohere model isn’t installed.` with `Install Model` / `Choose Method`, using M12's trusted installer/size/storage checks. |
| Original folder unavailable | `Waiting for access to {folder}.` with `Restore Access`. Restore/revalidate that binding; temporary errors do not imply permanent loss. |
| Upload evidence missing | `Waiting for iCloud upload verification.` with `Retry Verification`. Resume exact-version observation/commit reconciliation without transcription or title regeneration. |
| Unusable text / cutoff | `No usable diary text was found.` / `Transcription stopped after 10 minutes.` with `Retry`. |
| Unreadable recording | `This recording can’t be read.` with `Retry` / `Remove` when owned audio remains; absent/unsafe audio has an explained disabled retry. |
| Queue storage unavailable | `Pending work is paused because local storage isn’t available.` with `Retry`. Refresh/reconcile storage, not every job's inference state. |
| Other-install/unbound recording | Review-required Pending entry with `Resume` / `Remove`; no automatic claim or save. |
| Confirmed in-flight removal | `Cancelling` until all affected work and cleanup settle; repeated input cannot create another removal. |

Manual transcription Retry is allowed for a failed recording with retained audio, without a fixed attempt cap. Serialize against removal, prior inference, draft adoption, and commit; revalidate the current owner revision, invalidate old generations, and retire only positively owned obsolete candidate authority. Refresh current Settings/readiness and durably bind the new attempt before inference. Do not reuse prior method/model settings or switch methods automatically. If the selected method is unready, stay pending and offer applicable explicit choices. Repeated taps submit one intent; settings changes cannot rewrite an already claimed attempt's provenance.

Save/access/verification retry is a separate intent. Preserve the finalized draft, title, effective transcription provenance, asset identity, and stable timestamps; resume M14 or the M16 edit journal at its last trustworthy checkpoint. Access restoration retries automatically where approved, with bounded attempts and no tight loop. A waiting/failed/destination-blocked entry must not hold newer ready jobs. No UI action can release an inference worker or file barrier just because a timer expired.

Resume of restored recordings first verifies installation availability, confined receipt/audio ownership, actual playable source, and durable destination state. Unavailable Keychain/protected data waits; genuine missing/unreadable audio remains reviewable. Persist the current installation binding, fresh generation, and cleared old attempt/candidate/commit authority before allowing a new current-Settings attempt. Revalidate the original folder against the current account; an old bookmark cannot silently authorize publication after restore. Keep prior-install output isolated until safely retired under verified ownership. Remove is explicit review of only the positively owned pending data, not permission to scan/delete a restored folder. M16 restored edits instead resume their accepted body/candidate through their own journal after source/destination revalidation; never invoke recording Resume or retranscription for them.

## Per-recording destination replacement

1. `Restore Access` first attempts original-destination revalidation. Offer replacement only through an explicit user declaration that the original folder was removed or its access revoked. Repeated timeouts/network errors cannot make that declaration for the user. Bind the review/picker flow to the recording and expected destination revision.
2. Stage a replacement through the same positive iCloud, account identity, disclosure, and scope checks as M8. Cancellation, ambiguous/local/third-party provider rejection, identity change, or persistence failure leaves the original binding and local candidate intact. Do not overwrite Settings' active folder or another job's destination.
3. Serialize under the recording's mutation barrier; invalidate prior save/repair generations, request cancellation, and wait for old accessors to relinquish before committing the replacement. Recheck whether verified completion already won. Preserve and explain a finished asset rather than retargeting it.
4. Durably bind the new destination capability and incremented revision in a recoverable transaction with the job and commit state. Reopen verifies which revision committed; a crash between snapshot and job writes cannot leave a silently mixed destination. Reconcile old partial/publication evidence and retain narrowly scoped cleanup obligations. If prior publication is ambiguous, preserve candidates and surface recovery rather than publish a duplicate pair or delete unknown old files.
5. Resume the same verified draft/asset mapping against the replacement, with fresh publication/upload proof. No retranscription, inferred new folder search, cross-account retry, or stale callback to the old destination is allowed. If the replacement differs from the active folder, use the existing former-folder completion banner after actual completion.

## Recording removal and the completion race

The dialog explains removal of the selected recording and its private audio/draft; Cancel mutates nothing. The confirmation token binds the owner revision and destination/body/attempt generations. On acceptance, atomically decide under the same barrier used by inference handoff, title/draft adoption, save, repair, retarget, and conflict publication. If complete local pair verification and both exact upload reports already committed completion before confirmation, preserve the finished asset, return a completed outcome, and explain that it was saved. A stale Remove action cannot become finished-asset deletion.

Otherwise persist removal intent/tombstone and invalidate outstanding results before allowing any new publication. An in-progress writer must recheck this intent before its completion checkpoint; if the provider accessor cannot yet stop, keep Cancelling and the tombstone. Coordinate M10/M14 cancellation/settlement rather than queuing removal behind a writer that could commit a new completion after confirmation. A deadline fences results but never proves access ended. Inference, title, draft, repair, conflict, and save callbacks from obsolete revisions cannot create an asset or release the barrier on their own.

After relinquishment, remove only positively owned private artifacts and any proven job-owned unverified destination partials using checked coordinated operations. Do not delete external changes, shared audio, a verified finished pair, or an arbitrary path from a malformed record. Preserve ambiguous external resources with a recovery reason; known cleanup obligations that cannot settle remain durable and visible. Remove the live job/tombstone only when required cleanup is durable. Relaunch resumes cleanup idempotently, including a crash after one file is removed. Never report removal success while a writer still holds access or while a required known cleanup is unresolved. Actual deletion tests use explicitly disposable synthetic fixtures.

## Incomplete inspection, repair, and removal

Exchange the observed catalog/recovery handle for fresh destination/account, resource identity/version, confinement, and availability checks. A provider download timeout is a wait, not a missing component. Read safe bounded surviving text as inert content without inventing valid v1 fields from malformed front matter. Unsupported/malformed bodies may be shown only through a bounded safe text reader; unsafe references are never followed. Explain each missing/invalid/unsupported/duplicate/legacy-ambiguous component without treating unsupported content as a legacy format or migrating it.

For playable surviving audio, acquire a read-only recovery lease bound to that exact plain resource or protected snapshot. Validate containment, actual bytes/format/duration, source stability, and clean decoder EOF; use M15/M16 streaming bounds and shared session ownership. Apply 64 MiB and the applicable 301-second v1/60-minute evidenced-legacy bounds. If format cannot be safely classified, retain the resource with audio unavailable. Ambiguous sibling candidates never establish an automatic audio binding. Preview cannot edit/Favorite, repair, trigger context lookup, or auto-play. Releasing the preview waits for player/decoder relinquishment before deleting a private replay copy.

Reuse M14's automatic reopen repair only when a retained capture/edit candidate and private ownership record prove the exact expected files and revisions. A matching asset UUID, timestamp, content digest alone, or legacy-looking name cannot authorize repair. External edits or competing retained candidates route to conflict/recovery. The inspection screen does not invent missing body/audio or rerun transcription on a finished resource.

Offer Remove only after establishing a finite exact set of validated selected resources and proving no referenced file is shared by another asset. A paged/partial inventory cannot prove absence of other references; perform the necessary bounded reference check through completion, or keep removal unavailable with a reason. Unsafe references, duplicate-ID ownership ambiguity, unknown resource types, or unresolved version sets prevent a broad delete. Legacy ambiguity never authorizes deleting every plausible sibling; retain unproven/shared audio. Safe unsupported text can be inspected, but absence of a trusted pairing/deletion contract keeps removal unavailable.

Persist a cleanup journal bound to the exact resources shown, their identities/versions, account/destination, and user confirmation. Revalidate immediately before each coordinated unlink; changed/new resources require refreshed review and confirmation. Never recursively delete a user folder or entire `.assets` directory containing unknown files. Delete only explicitly authorized regular resources, removing an owned empty container only after checking its unchanged identity and contents. A replacement appearing at the same path survives. A crash after partial deletion resumes only positively proven remaining operations; changed/shared resources stop cleanup and retain an entry-level explanation. If journal persistence fails, do not start deletion. Deletion is logical cleanup; it cannot erase old backups, remote history, or recipient copies.

## Conflict inspection and choice

Obtain protected complete-pair snapshots from the owning capture commit, external committed resource, or M16 submitted edit. Validate actual Markdown/audio binding, safe files, supported fields, and provider version identity for each. Equal content or asset IDs do not establish ownership or a pairing. A local submitted candidate carries no iCloud time. Two Markdown revisions may bind the same uniquely validated unchanged audio, with independently recoverable pair snapshots; shared audio must not be deleted while the selected version still uses it. If versions cannot be paired uniquely, or additional unknown provider versions remain, preserve them and explain why resolution/cleanup is blocked rather than selecting the first two.

Only apply `DiaryPairConflictPolicy` to validated complete provider pairs: one wins automatically only when both file modification times are strictly later. Equal, missing, cross-ordered, or shared-audio times and unpublished local candidates require choice. Do not use front-matter `updated_at`, device time, title, lexical order, or a rewritten audio timestamp as a tie-breaker. M14's automatic later-pair path keeps its verification/upload/final-check safeguards; viewing the recovery screen adds no automatic deletion authority.

Present two separately openable, vertically scrollable tabs, `Version 1` and `Version 2`, with available modification dates as accessibility values. Preserve tab-to-snapshot identity during refresh; do not silently swap bodies beneath a chosen tab. Load bounded text and acquire snapshot-specific audio leases on demand. Show unknown dates as unavailable without fabricating times. Both versions stay read-only. A changed snapshot/destination clears preview action authority and asks for refreshed review; normal VoiceOver reading of visible content remains available.

Selection and obsolete-version removal are separate durable intents. A transient highlighted tab is not a committed choice. Validate and journal the explicit selected snapshot against the reviewed candidate set before chosen-pair publication. Ask for confirmation before deleting the unchosen version, binding consent to the selected/unchosen snapshots, their exact versions, owner/body/destination revisions, and current account. The current job-ID-only confirmation entry point must be extended to reject stale consent. Cancel/back from confirmation preserves both recovery copies and never implies permission to delete; if selection was already durable, explain its pending cleanup state without assuming it was rolled back. Repeated submissions are idempotent.

Reuse M14/M16 checked publication and reconciliation for the chosen pair. Persist each audio/Markdown checkpoint as applicable, verify the exact complete pair, obtain separate successful upload reports for both versions, and recheck unchanged versions before cleanup. A normal text-only resolution need not rewrite unchanged audio merely to obtain a new timestamp. Confirmation may be recorded before uploads settle, but deletion remains blocked until proof exists. Revalidate the provider version inventory immediately before obsolete cleanup; any new/unknown version invalidates the old cleanup authority and retains recovery copies. Remove only recognized obsolete versions not referenced by the chosen pair. Record durable completion before private snapshots/candidates are cleaned. Interrupted publication or cleanup resumes its journal without asking the user to make an already durable identical choice again; changed candidate sets require new review/confirmation.

## Resource, interface, and privacy rules

Keep list projections lightweight and fetch only the displayed bounded preview(s). Incrementally stream/decode; do not allocate whole audio/PCM or every transaction body. Use M15/M16 measured decode/cancellation budgets for long eligible legacy audio. Settle scopes/accessors before releasing loans or starting replacement work; cap concurrently unsettled operations rather than accumulating retries. Malformed recovery records and disk/protected-store failures preserve source data and allow unrelated valid work where durable progress remains possible.

Reuse approved monochrome custom template recovery/action icons at the canonical sizes with at least 44-by-44-point targets; extend the existing icon pipeline only as needed. Do not introduce SF Symbols/vector substitutes or new build tools. Visible labels are accessibility names; expose enabled, selected, waiting, and Cancelling states independently of color. Preserve focus after row updates, readable entry reasons, scrollable long content, largest Dynamic Type, keyboard-independent confirmation actions, VoiceOver tab/selection semantics, and Reduce Motion. Recovery replay uses `Play audio`, `Pause audio`, and adjustable `Audio position` with `{elapsed} of {total}` and 15-second steps. Capture keeps session priority and its sole Stop & Transcribe control.

The neutral cover includes recovery text/audio previews, tabs, picker/confirmation overlays, and former-folder notices before nonforeground snapshots. Stop replay and invalidate visible action sessions on nonforeground/account/folder transitions; durably accepted work retains its owner binding for later reconciliation. Render all text inertly with no interactive links, HTML, remote images, or automatic fetches. Keep bodies/titles/audio/coordinates/paths/bookmarks/provider IDs/raw errors out of diagnostics, accessibility identifiers, and stored navigation. Evidence uses sanitized codes, counts, durations, and opaque references. M17 neither requests notification permission nor creates reminder content.

## Evidence boundaries and escalation

M17 implements the existing P1-M5 outcomes; it introduces no owner decision about method policy, conflict order, folder scope, or deletion scope. If an actual provider/runtime cannot enforce checked ownership, cancellation settlement, upload proof, or version-bound cleanup, retain the candidate/recovery state and report the concrete evidence gap. Ask before changing an approved outcome, dependency/build tool, or legacy format contract; do not substitute an inferred safe-enough deletion or silently weaken the milestone gate.
