# P1-M18: Optional context and pending-work reminders overview

Status: Planned

Add optional recording-start location and weather to new Diary Snippets, and one local reminder when diary work remains pending after app departure. Keep capture, transcription, saving, and in-app recovery usable when permissions, lookups, notification delivery, or platform services are unavailable.

## Owner decisions and stages, 2026-11-11

- **Two stages, reminder first.** **M18a** is the pending-work reminder; **M18b** is location, place and weather context. Each has its own checklist items (tagged below) and device scenarios, so a provider or account blocker in M18b cannot hold up M18a. M18 is Done when both stages are Done or the owner explicitly defers M18b.
- **Weather source: Open-Meteo.** WeatherKit is not used because it needs a paid Apple Developer Program membership. Terms verified from Open-Meteo's own pages on 2026-11-11 (see the [research record](milestone-18-open-meteo-research.md) and the [approach](milestone-18-context-reminders-architecture.md#open-meteo-terms-verified-2026-11-11)): the free API is for non-commercial use only, which its terms exemplify as private or non-profit apps without subscriptions or advertising; it needs no key; limits are 600/min, 5,000/hour and 10,000/day per IP and application; attribution is required next to displayed data; and there is no uptime guarantee. The pages do not address App Store distribution, so this choice assumes a personal, ad-free, subscription-free app; get written confirmation from Open-Meteo before any public release and revisit if the app is ever monetized. Weather is not required for any entry: a failed or throttled lookup omits it.
- **Weather privacy.** Weather has its own Settings toggle, **default Off**, with a disclosure that rounded coordinates, the start time and the device's IP address are sent to Open-Meteo, which may keep web-server logs, possibly including coordinates, for 90 days. Location and place label work without it. The request sends coordinates rounded to two decimals (about 1 km); stored location keeps the exact returned coordinates. No audio, text or account identifier is sent; the IP address cannot be withheld. This amends the approved Apple-only weather boundary and the P1-M5 weather attribution contract.
- **Manual snippets.** Manual text-only snippets (M21 Task 15) get location and weather context as well. The context instant is the first Save, with bounded acquisition beginning then, never delaying the save acknowledgment, and accepted only before initial commit. This amends the product statement that manual snippets carry no location or weather fields; the schema 2 manual codec, Metadata display and edit preservation must be extended and tested accordingly.
- **Reminder eligibility.** Failed-only recordings stay excluded. Waiting manual saves (All → Pending Diary Snippets) count as pending work.
- **Documentation reconciled 2026-11-11:** [product behavior](../product-behavior.md), [architecture](../architecture.md), [UX GUI](../ux-gui.md), [P1-M5](milestone-05-decisions-architecture.md) and the [security review](../security-review.md) (new SEC-09) now state these decisions. Still open at implementation: M15's Apple-attribution code and the schema 2 manual codec.

## Implementation prerequisites

- **Actual start event:** `CaptureCoordinator` establishes `CaptureIdentity`, but composition must explicitly notify context acquisition only after audio starts successfully. A Record tap, permission sheet, or failed capture must not start a lookup. Context must never delay capture settlement while locked.
- **Durable metadata handoff:** `DiaryDraftFactory` currently supplies `location: nil, weather: nil`; capture receipts and queue jobs have no context binding. Add a confined, installation-bound context record and a verified snapshot handoff into draft creation/publication, including crash reconciliation and compatibility with older jobs.
- **Publication authority:** context sealing and opt-out must serialize with M14's exact Markdown digest/commit claim. An already prepared draft or commit record cannot authorize a later stale context write; uncertain or partly published state retains M14 recovery/proof duties.
- **Pending observation and lifecycle:** current `AppModel` arrays are presentation projections, and `becameActive()` is also called from Settings. Add a typed durable pending observation and genuine app-departure input; permission/picker interruptions and view appearance must not reset the reminder clock.
- **Weather provider (M18b):** add a `WeatherPort` backed by an `URLSession` adapter for Open-Meteo's current-conditions endpoint over HTTPS with App Transport Security, a fixed host allowlist, response size and time limits, and strict decoding. Map WMO weather codes to a fixed English summary and validate the observation time. No new package, key or entitlement is needed. Record the attribution text and link from the live terms.

## Scope

| Work | Required behavior |
|---|---|
| Weather toggle (M18b) | Separate Settings switch, default Off, with the third-party disclosure above. Check it before every weather request and before accepting a result; turning it Off cancels and fences lookups like location opt-out. |
| Location preference and permission | Retain first-launch optional When In Use permission and add the app preference to the existing Settings location section. Check preference and live authorization before acquisition, outbound lookup, result acceptance, and metadata publication. Denial, Allow Once expiry, reduced accuracy, and opt-out never block recording or trigger surprise prompts. |
| Recording-start context | Begin bounded acquisition at successful capture start. Accept valid location within the approved five-minute/500 m contract; preserve the returned coordinates without rounding or substituting geocoded coordinates. Place failure keeps coordinates. Accept weather observed within 60 minutes of recording start, store Celsius, and omit unavailable complete groups. Manual snippets use the first Save as the start instant. |
| Durability and publication | Retain only validated recording-bound context in protected, backup-excluded staging. Freeze available context without waiting when drafting/publishing starts. Retry/relaunch/retargeting reuses accepted start context without reacquisition; late results cannot backfill a draft or saved asset. Serialize revocation, removal, and initial publication; clean context staging with its owning job. |
| Metadata | Reuse bottom Metadata, coordinate fallback, system measurement formatting, and Open-Meteo attribution beneath displayed weather. Show Metadata for manual snippets only when context exists. Browsing and edits never acquire or refresh context. Preserve existing/legacy metadata and unknown or malformed optional scalar fields under the established codec/edit rules. |
| Reminder permission | Ask only when the first reminder becomes necessary and the app can present the request in the foreground. Persist the request-attempt guard, check live notification settings, and retain a nonblocking Open Settings path on denial without repeated prompts. Never present a permission sheet during active capture or from the background. |
| Reminder lifecycle | Maintain at most one generic, nonrepeating local request for eligible pending work. Anchor it to actual app departure, target the next local calendar day at the same wall time, reconcile on reopen with the current timezone and next valid DST time, and cancel when eligible work clears. Background capture settlement can update eligibility without moving the departure time. |
| Eligible work | Queued, processing and waiting recordings, accepted edits awaiting publication, and waiting manual saves count. Failed-only recordings and standalone recovery assets do not. A Danger Zone staging purge that clears the last item cancels the reminder. |
| Recovery and privacy | Keep Main/All pending state authoritative regardless of reminder failure/delivery. A notification opens All and rechecks current state. Its text is exactly `You have pending diary work.`; payload, logs, previews, and errors carry no diary/location/destination content. |

## Out of scope

No background location/tracking, Always or temporary precise-location request, later weather backfill, saved-metadata editor/removal, weather provider other than Open-Meteo, hosted inference, APNs, background inference, recurring daily nag, reminder time picker, new root destination, or guarantee of notification delivery. Planning performs no account/capability change or user-data mutation.

## Completion checklist

- [ ] [M18a+b] Typed context, preference, pending observation, calendar/clock, and reminder ports preserve inward dependencies. Platform locations/weather/notification objects, URLs, and raw errors stay inside adapters; old settings/jobs without M18 fields remain readable without invented context.
- [ ] [M18b] Successful recording start launches one bounded context operation with immutable start/installation/recording identity. Failed starts launch none. Capture start, Stop & Transcribe, locked settlement, inference, title generation, and save never await a location/weather result.
- [ ] [M18b] Location freshness/accuracy, finite coordinate ranges, exact returned values, current authorization/preference, and weather start-time tolerance are validated at the boundaries. Exact and just-outside thresholds, reduced accuracy, future/invalid dates, and hostile/oversized strings are covered. Geocoding failure retains coordinates; weather failure omits weather without failing the job.
- [ ] [M18b] The Settings preference persists safely, preserves older settings, and cannot override system denial. Permission changes/opt-out cancel and fence lookups, clear unpublished context authority, and prevent stale results or retries from publishing it. No repeated/implicit permission requests or background location capability are introduced.
- [ ] [M18b] A versioned, bounded, protected, backup-excluded context record survives capture-to-queue adoption, draft construction, retries, and crashes. Wrong-install/unbound/malformed records are isolated; restored work never triggers context lookup or publication before its owner's review. Missing optional context remains omission, not a failed recording.
- [ ] [M18b] Snapshot sealing, private-draft binding, and M14 publication serialize with revocation/removal. Draft/commit digests cannot disagree; an early save proceeds with available groups and rejects later enrichment. Partial publication, protected-data failure, changed destination, and late callbacks preserve recovery copies and existing upload/cleanup guarantees.
- [ ] [M18b] Stored accepted context keeps its start instant through delayed processing, current-Settings transcription Retry, destination restoration, body/Favorite edits, and sync. No reopen, detail visit, model readiness change, or resumed upload reacquires or backfills context. Verified completion/confirmed removal cleans only positively owned context staging.
- [ ] [M18b] Open-Meteo lookups work on the target phone through the allowlisted HTTPS adapter, including offline, timeout, throttled, malformed and oversized responses. Temperature uses system measurement formatting; coordinate fallback and Open-Meteo attribution appear in Metadata in English/Korean and light/dark. No weather appears without its attribution. Inspect outbound requests: only rounded coordinates, the requested variables and time, with no app-supplied identifiers.
- [ ] [M18a] Durable pending observation deduplicates adopted captures/jobs/accepted edits and waiting manual submissions, includes prerequisite/save/upload/review/removal waits across original folders, and distinguishes unknown storage from verified empty. Failed-only or external catalog recovery does not create a pending reminder; retry/Resume changes eligibility through the owning state machine. Purge and automatic upload verification update eligibility.
- [ ] [M18a] Notification authorization is requested once in context when first needed, with a persisted attempt guard and no capture/background prompt. Denied/disabled/changed authorization, Allow Once location sheets, installation restore, add/cancel failure, and permission-result races preserve in-app recovery without repeat prompts or false scheduling success.
- [ ] [M18a] One nonrepeating generic request uses real background departure and next-local-day calendar arithmetic, current-timezone reopen reconciliation, next-valid DST handling, and a verified trigger date. Duplicate lifecycle callbacks, Settings appearance, cross-midnight capture settlement, rapid reopen/departure, overdue requests, clock/calendar changes, and stale add/cancel completions cannot duplicate or resurrect an obsolete reminder.
- [ ] [M18a] Completion/removal of the last eligible item cancels pending and stale delivered reminders as soon as observed. Unknown/inaccessible state is not treated as empty; old notification taps revalidate and open current All state without restarting work or exposing stale content. Foreground delivery does not compete with the existing in-app notice.
- [ ] Focused policy, adapter, storage/fault, lifecycle, calendar, race, and privacy checks cover the [approach](milestone-18-context-reminders-architecture.md), including applicable [V-04, V-08, V-09, and V-12](../security-review.md#adversarial-verification-matrix) cases.
