# P1-M1: WhisperKit and FluidAudio Swift SDKs

Status: Active

Research checked on 2026-11-01 for the iPhone 17 Pro Max and five-minute en-US/ko-KR diary recordings. Both SDKs offer Swift/Core ML local speech paths, but their model catalogs, Korean coverage, and long-audio handling differ. Neither SDK or model is approved as a v1 transcription method by this research.

## Comparison for this app

## FluidAudio Korean candidates and measured evidence

- **Cohere Transcribe:** The mixed-precision Core ML path uses an approximately 1.8 GB INT8 encoder plus a separate FP16 decoder, so it is a substantial download and memory candidate. Its current v3 decoder expands the output-token budget to avoid omissions observed with earlier dense-speech windows. The implementer warns that routing the encoder through the GPU can inflate Mac memory by about 10 GB and recommends the Neural Engine path on iOS; phone memory still needs measurement. [Implementation notes](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md) On **M4 Pro, 48 GB**, its FLEURS short-clip benchmark reports en-US WER 5.63% and ko-KR CER 6.67% (ko-KR WER 16.39%), with reported throughput factors 2.49× and 1.84× respectively. These are read-speech, Mac, single-window results, not five-minute iPhone measurements. [Benchmark](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md#fleurs-int8-encoder--fp16-cache-external-decoder) See the [dedicated Cohere iPhone research](p1-m1-cohere-transcribe-iphone.md) for GGUF/Metal and Swift/MLX alternatives and the efficiency trial.
- **SenseVoiceSmall:** FluidAudio lists a [Core ML conversion](https://huggingface.co/FluidInference/sensevoice-small-coreml) with an approximately 225 MB INT8 encoder and a `SenseVoiceManager`; its [catalog](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Models.md) says non-autoregressive models can use an overlapping sliding-window path for long audio. The model card marks its license `sensevoice-upstream`, so terms require review before approval. Its published parity results cover English and Chinese, not Korean on the target phone. The [upstream released checkpoint](https://github.com/QwenAudio/SenseVoice) lists English and Korean among its supported languages; the conversion's broader "50+ languages" claim should not be read as verified coverage for that checkpoint.
- The [FluidAudio model catalog](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Models.md) lists Qwen3-ForcedAligner-0.6B as evaluated but unsupported. FluidAudio should not be assumed to run Qwen3-ASR or the forced aligner just because it is a local audio SDK.

No authoritative benchmark found in the reviewed SDK docs establishes five-minute English/Korean diary quality, cold/warm latency, peak memory, battery, or thermal behavior on an **iPhone 17 Pro Max** for either SDK. Argmax's recommended model and FluidAudio's Mac benchmarks are useful candidates for a physical-device comparison, not target-device performance claims. For FluidAudio/Cohere, also record any truncated or capped windows and transcript errors at the 30-second hops; for WhisperKit, inspect VAD chunk boundaries and word timestamps against hand-labeled audio.

## Decision implication

The confirmed v1 method set remains [Apple on-device and hosted Qwen](../product-behavior.md). If another local method is desired, compare WhisperKit multilingual variants, FluidAudio's Korean-capable path, whisper.cpp, and on-device Qwen3-ASR on the **same** en-US/ko-KR diary clips, with download/install behavior and package/model license review. The owner must approve a runtime, exact model, distribution strategy, and acceptance targets before integration. Optional word timing is a separate product and schema decision; see the [forced-aligner research](p1-m1-qwen3-forced-aligner-iphone.md).
