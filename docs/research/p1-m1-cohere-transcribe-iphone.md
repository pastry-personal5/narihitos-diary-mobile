# P1-M1: On-device Cohere Transcribe on iPhone 17 Pro Max

Status: Done

Research checked on 2026-11-01 for **ASR only** on five-minute en-US and ko-KR diary recordings. The multilingual Cohere Transcribe 03-2026 checkpoint has Core ML, GGUF/Metal, and Swift/MLX integration paths. The owner subsequently selected the runtime-publisher Q4_K_M GGUF with `transcribe.cpp` and Metal as the P1-M12 implementation direction based on the [P1-M6 target-phone trial](../phase-1/milestone-06-cohere-runtime-trial-results.md). That short-file trial did not establish five-minute quality, energy, cancellation settlement, or WER/CER.

## P1-M6 result

On an iPhone 17 Pro Max running iOS 27.0.1, Q4_K_M completed the available short English and Korean clips with Metal, about 1.73–1.75 GB observed peak footprint, and lower observed load/inference time than Q5_K_M. Q4 and Q5 returned identical English text; their Korean text differed without a reference score. Production must use trusted manifest provenance, explicit language, complete-output checks, no automatic CPU fallback, and silence-aware chunks no longer than 45 seconds until long input is proven complete. P1-M12 retains chunk-seam and cancellation verification; P1-M19 retains complete-experience device evidence.

## Model and language fit

- [CohereLabs/cohere-transcribe-03-2026](https://huggingface.co/CohereLabs/cohere-transcribe-03-2026) is a 2B-parameter Conformer encoder/Transformer decoder ASR model under Apache-2.0. Its 14 training languages include English and Korean. Select `en` or `ko` from the app's recorded language hint; the model has no explicit automatic language detection, handles code switching inconsistently, and returns text without word timestamps or speaker labels. Cohere recommends a noise gate or VAD for silence hallucinations; the effect on quiet diary speech needs testing. These are model limits shared by the local conversions. The original Hugging Face weights currently require accepting access conditions; review the exact conversion's terms and distribution path before a model download is designed.
- [Cohere Transcribe Arabic 07-2026](https://huggingface.co/CohereLabs/cohere-transcribe-arabic-07-2026) is optimized for Arabic and English, not Korean. It is not a single-model match for this app's two languages.
- Cohere's official [Transformers example](https://huggingface.co/CohereLabs/cohere-transcribe-03-2026#usage) chunks audio longer than the feature extractor window. Its server-side leaderboard numbers are not mobile benchmarks. An app can add language detection around Cohere, as [Superwhisper's release notes](https://apps.apple.com/us/app/superwhisper-ai-dictation/id6471464415) advertise; that does not add native language detection to the checkpoint.

Validate five-minute Korean/English chunk joins, 4-bit quality, and actual phone memory before treating this as a deployable path. |

Two smaller third-party Core ML uploads advertise [INT4 at about 1.1 GB](https://huggingface.co/MarkChen1214/cohere-transcribe-03-2026-CoreML-INT4) and [6-bit compression](https://huggingface.co/BarathwajAnandan/cohere-transcribe-03-2026-CoreML-6bit), but both model repositories are marked GPL-3.0. A separate [Swift MLX Cohere port](https://github.com/neo773/cohere-transcribe-mlx) is **macOS-only as documented**. Although its checkpoint is about 1.5 GB on disk, its author says it materializes FP16 weights and needs roughly **4.7 GB resident / 5 GB free GPU memory** while transcribing. This is a concrete reason to measure each implementation's working set rather than infer it from quantized file size; the 256 MB MLX cache cap in that README is specific to that port, not a verified iPhone setting for MLX Audio Swift.

FluidAudio's [M5 Pro compute-unit comparison](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md#compute-units-and-memory) shows why the configuration matters: for a 16.9-second clip processed through the fixed 35-second encoder shape, `.cpuAndNeuralEngine` took about 1.15–1.23 seconds per warm encoder pass, while GPU placement took about 0.5 seconds but increased the settled Mac process footprint by roughly 0.9 GB and maximum RSS by several GB. The report also distinguishes process `phys_footprint` from maximum RSS. A separate [M2 cold-start example](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md#cold-start-vs-warm-inference-isolated-single-process) spent about 186 seconds compiling its first encoder call, versus 2–3 seconds on warm calls. Neither Mac behavior can be projected into a phone latency or memory limit.

Before P1-M6, the reviewed public material provided **iPhone deployment evidence**, but no reproducible target-phone performance result: [Superwhisper's iPhone page](https://superwhisper.com/voice-to-text-iphone) says its downloadable Cohere speech model runs offline on the phone, and its [iPhone App Store notes](https://apps.apple.com/us/app/superwhisper-ai-dictation/id6471464415) introduced on-device Cohere as an experimental model in version 2.19. [Spokenly's own guide](https://spokenly.app/blog/cohere-transcribe) says its Q4 variant downloads about 1 GB, uses roughly 1.7 GB while loaded, and runs locally on iPhone with iOS 18+; it does not name the conversion or explain the memory measurement. Spokenly distinguishes this from its Mac-only INT8 Core ML variant, which it says uses about 10 GB while running. Neither app discloses a measured iPhone 17 Pro Max configuration or five-minute en-US/ko-KR accuracy, latency, peak memory, battery, and thermal results. Superwhisper's [public Cohere benchmark](https://superwhisper.com/benchmarks/cohere-transcribe) uses Apple **M4/M4 Max Macs**, so its speed cannot be quoted as iPhone speed. The [Cohere model card](https://huggingface.co/CohereLabs/cohere-transcribe-03-2026#ecosystem-support-) also lists iOS apps, but does not supply phone measurements.

## Original iPhone trial recommendations

1. **Install before offering an offline method.** Keep the recording in its existing `.m4a` file, download or stage one model conversion, and show a readiness state. Decode to 16 kHz mono Float32 for FluidAudio or MLX via an iOS audio converter; the GGUF path needs 16 kHz mono input through the binding or a converted WAV. The five-minute Float32 buffer is about **19.2 MB** by calculation, excluding decoder and model workspace; chunked decode can avoid keeping it all in memory if needed. Count model files and Core ML/Metal caches in storage measurements, not just the download size. [FluidAudio AudioConverter](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/API.md), [MLX Audio Swift input](https://github.com/Blaizzy/mlx-audio-swift/blob/main/Sources/MLXAudioSTT/Models/CohereTranscribe/README.md)
2. **Start Core ML with its documented default placement.** Use FluidAudio's INT8 encoder, FP16 **v3** decoder, and the [default `.cpuAndNeuralEngine` compute units](https://github.com/FluidInference/FluidAudio/blob/main/Sources/FluidAudio/ASR/Cohere/CoherePipeline.swift). Check whether it fits the phone's app memory limit before processing a long file; the MacParakeet q8 RSS result makes file size an inadequate safety proxy. Do not choose `.all` merely for a Mac warm-speed gain. Load models once for a foreground queue run and reuse them across jobs; compare first use, warm reuse, and reload after app termination. This reuse is a trial hypothesis drawn from the published cold/warm gap, not a proven iPhone optimization.
3. **Use the right long-audio path and detect incomplete results.** For Core ML call `transcribeLong` on five-minute files, pass `.english` or `.korean`, and record `cappedWindows` and any seam omissions or duplicated text. For GGUF, compare one 300-second call with shorter, overlapped chunks; handle `INPUT_TOO_LONG`, `OUTPUT_TRUNCATED`, repetition, and out-of-memory statuses as failed or partial jobs rather than publishing a complete diary asset. For MLX Audio Swift, compare fixed low-energy splitting with optional VAD on both languages, checking whether quiet speech is removed or seams repeat words. [FluidAudio API](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md), [GGUF input contract](https://github.com/handy-computer/transcribe.cpp/blob/main/docs/input-limits.md), [MLX chunking notes](https://github.com/Blaizzy/mlx-audio-swift/blob/main/Sources/MLXAudioSTT/Models/CohereTranscribe/README.md#optional-vad-pre-processing)
4. **Compare the compact configurations on the actual phone.** Use the same consented 30-second and five-minute en-US/ko-KR diary-like files for Core ML INT8/FP16, GGUF Q5_K_M and Q4_K_M, and MLX 4-bit if its iOS build and weight loading succeed. Q5 has published FLEURS quality for both languages; Q4 and MLX 4-bit need particular Korean quality checks. Record cold install/load and warm transcription wall time, WER for English and CER for Korean with one normalization policy, peak app memory, model-plus-cache storage, truncated/capped outputs, silence and code-switch behavior, and back-to-back runs. Use Xcode's [memory tools](https://developer.apple.com/documentation/xcode/gathering-information-about-memory-use), [Power Profiler](https://developer.apple.com/documentation/Xcode/measuring-your-app-s-power-use-with-power-profiler), and [thermal state](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum) on the physical phone. Keep the screen, charge level, network state, and ambient temperature comparable.
5. **Treat phone memory as a measured limit.** On load and before each long job, log [current available process memory](https://developer.apple.com/documentation/os/os_proc_available_memory) as advisory data, plus peak footprint and any [jetsam report](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports). The operating system's process limit can change; total device RAM or model-file size does not establish a safe app budget. Repeat after an app relaunch and a model swap, when cache residency may differ.

P1-M6 resolved the implementation direction in favor of Q4_K_M GGUF/Metal; the recommendations above remain historical context for evidence that was not gathered. These ASR routes can produce local transcript text after model installation, but the checkpoint does not produce word timestamps; see the [forced-aligner research](p1-m1-qwen3-forced-aligner-iphone.md) only if timing becomes a separate requirement. The confirmed v1 methods are [Apple on-device transcription and on-device Cohere](../product-behavior.md); hosted Qwen is future work.
